# 工业级电商 ERP 成熟度评估报告（2026-04-13）

## 1. 评估范围

本次评估面向“工业级、可收费、对标企业级电商 ERP”的目标，而不是面向单次演示。评估包含以下内容：

- 本地代码与页面结构：前端路由、菜单、页面、API 模块、OpenAPI、后端集成测试。
- 本地文档体系：功能目录、流程文档、上线门禁、专项设计与历史报告。
- 外部能力基线：参考 Oracle NetSuite、Microsoft Dynamics 365、SAP Business One、Odoo 官方资料中稳定出现的 ERP 能力域。

### 1.1 外部能力基线映射

| 外部参考产品 | 本次主要借鉴的能力域 |
| --- | --- |
| Oracle NetSuite | 财务管理、订单管理、库存管理、采购、CRM、一体化业务骨架 |
| Microsoft Dynamics 365 | 仓储管理、供应链、财务、组织与企业级流程治理 |
| SAP Business One | 销售、采购、库存、财务、服务管理的一体化模块边界 |
| Odoo | 多公司、帮助台、审批、质量、员工协作等扩展能力域 |

本次评估不照搬品牌命名，而是提炼这些成熟产品中长期稳定存在的能力域，作为本项目目标蓝图和上线范围的外部校准基线。

## 2. 证据基线

本次扫描得到的项目现实如下：

- 前端菜单叶子项约 `159` 个。
- 前端路由定义约 `182` 个。
- 前端页面组件约 `208` 个。
- 前端 API 模块约 `160` 个。
- `crates/erp-api/tests` 中可见集成 / 权限 / 主链路测试文件 `39` 个。
- `openapi/erp_api_v1.yaml` 中按路径行计数，可见约 `475` 条 `/v1/` 路径定义。
- 页面中至少有 `8` 个明显占位页，且代码扫描可见约 `32` 处 placeholder / 待接入痕迹。

结论：本项目已经明显不是“从零起步”，而是进入了“骨架很宽、主链路已成形、但产品级一致性不足”的阶段。

## 3. 总体判断

### 3.1 三个视角的成熟度

| 视角 | 结论 | 估算成熟度 |
| --- | --- | --- |
| 核心交易链路成熟度 | 平台接入 + OMS + WMS + 基础治理已经具备试点基础 | 68 / 100 |
| 经营级上线成熟度 | 加上采购、计划、售后、财务、报表后，可形成首批收费版本，但仍需补齐关键短板 | 52 / 100 |
| 工业级商业化成熟度 | 若目标是多商户、多组织、强财务、强协同、强质量的成熟 ERP，目前仍在中前段 | 43 / 100 |

### 3.2 一句话结论

当前项目适合继续冲刺“首批客户试点版”，但还不适合直接承诺“多商户、多组织、全面经营闭环”的成熟商业版上线。

## 4. 领域评分

评分规则：

- `1`：只有概念或占位。
- `2`：有页面 / API / 文档，但闭环弱。
- `3`：主流程可走，仍缺生产细节。
- `4`：可收费上线，需持续优化。
- `5`：成熟工业化能力。

| 领域 | 评分 | 说明 |
| --- | --- | --- |
| 平台与租户基础 | 3.5 / 5 | 多租户、RBAC、流程治理、审计和门禁有良好骨架，但多商户与多组织模型缺失 |
| 渠道与店铺接入 | 3.5 / 5 | 平台适配器、OAuth、Webhook、同步健康已有明确实现方向，但补偿与运营化仍需加强 |
| 商品与主数据 | 2.5 / 5 | 页面和 API 很多，但主数据治理、供应商货品档案、质量属性、去重责任链不足 |
| 销售与 OMS | 3.0 / 5 | 审单、异常、映射修复、订单工作台已有可用基础，拆合单、结算、发票仍偏浅 |
| 仓储与库存 | 3.0 / 5 | WMS 主域覆盖广，出入库、波次、盘点、调拨线索齐全，但现场执行深度不足 |
| 物流与履约 | 2.5 / 5 | 目录、轨迹、异常、结算、安装均有页面，但选路、承运商 SLA 和账单闭环待增强 |
| 采购与计划 | 2.5 / 5 | 页面齐全，但从“有模块”到“可执行闭环”还差审批、回写与经营反馈 |
| 客户与售后 | 2.5 / 5 | CRM 和售后模块布局广，但客户 360、客服中心、售后财务联动仍弱 |
| 财务与管理会计 | 2.0 / 5 | 有应收应付、成本、利润、发票入口，但离成熟财务经营闭环差距仍大 |
| 营销与价格 | 1.8 / 5 | 功能入口已铺设，但多数仍停留在原型或轻量阶段 |
| 报表与驾驶舱 | 2.5 / 5 | 已有统计页和经营分析入口，但真正的管理驾驶舱与钻取能力还不够 |
| 组织、质量与协同 | 1.2 / 5 | 这是当前最薄弱的域，只有零散能力，没有形成产品化中心 |
| 非功能与工程治理 | 3.5 / 5 | OpenAPI、release gate、测试、Runbook、可观测性明显强于多数早期项目 |

## 5. 当前最大的优势

- 架构主线清楚：`erp-channel -> inbox/outbox -> dispatcher -> worker -> erp-api` 的链路设计合理，适合工业化演进。
- 代码规模已经形成广覆盖：前端路由、页面、API 和后端测试都不是简单原型级体量。
- 发布治理意识较强：已有 `release gate`、OpenAPI 校验、后端 smoke、E2E、Runbook 和安全门禁。
- OMS / WMS / 系统治理的设计强于一般“先做 UI”的项目，说明项目已经开始考虑生产环境而不仅是演示。

## 6. 当前最大的短板

### 6.1 菜单信息架构还不够像正式产品

当前菜单可以看出“模块已经很多”，但还看不出“产品结构已经稳定”。

最明显的问题包括：

- `财务` 被放在 `统计` 下面，导致财务域被误当成报表附属能力。
- `售后处理` 被放在 `客户` 下面，造成 CRM 与逆向供应链边界模糊。
- `销售` 菜单混入了下载任务、物流上传、包裹、策略设置等多种职责。
- `系统` 菜单混入研发 / 演示性质入口，生产与工程边界未分离。
- `目录` 顶层菜单仍然过重，主数据尚未被产品化地分配到各业务域。

这会直接影响后续三件事：

- 新客户培训成本高。
- 权限设计难以稳定。
- 后续新功能容易继续堆菜单而不是进入清晰架构。

### 6.2 多商户和多组织仍未形成真正产品能力

项目现在更接近“多租户 + 多店铺 + 多平台”的基础形态，而不是成熟的“多商户 + 多组织 + 多法人结算”。

对标收费产品时，这一层非常关键，因为它决定：

- 是否能服务代运营、集团化商家或多个经营主体。
- 是否能做商户级结算、商户级账单和商户级经营看板。
- 是否能在一个系统内容纳多个组织边界而不产生权限混乱。

### 6.3 财务域还不足以支撑成熟商业交付

财务入口已经存在，但从工业级 ERP 的角度看，目前更接近“经营分析辅助模块”，还不是“严肃经营闭环”。

最关键的缺口是：

- 应收 / 应付 / 对账 / 开票之间还需要更强的单据闭环。
- 成本口径与费用分摊需要更稳定的版本化规则。
- 代销、税务、多主体结算仍处于扩展阶段。

### 6.4 组织、审批、任务中心、质量体系偏弱

企业级 ERP 的客户不会只买交易链路，他们还会买：

- 跨部门审批。
- 任务和 SLA 跟踪。
- 质检 / 召回 / 归因。
- 知识沉淀与 SOP 执行。

目前这些域在本项目里还没有形成正式中心，是工业化阶段最大的结构性短板之一。

## 7. 上线可行性判断

### 7.1 可以推进的上线范围

在以下前提下，可以推进首批客户试点版：

- 单商户或单主体。
- 2 到 4 个核心平台。
- 多店铺、多仓，但组织层次相对简单。
- 财务只要求经营核算和基础对账，不要求完整总账体系。
- 仓储以桌面工作台为主，不强依赖 PDA 和自动化设备。

### 7.2 暂不建议承诺的上线范围

当前不建议直接承诺以下能力：

- 多商户统一运营与商户结算平台。
- 多法人、多组织、跨主体财务结算。
- 完整的审批中心、任务中心和质量体系。
- 面向大型仓的移动端 / PDA / 自动化设备深度执行。
- 复杂营销与价格引擎。

## 8. 上线前必须先补的事项

### 8.1 P0 必补

- 统一菜单信息架构，按 `渠道与店铺 / 销售 OMS / 商品与主数据 / 仓储 WMS / 物流 TMS / 财务结算 / 系统治理` 重构。
- 补齐订单拆合单、销售结算、销售对账、发票联动的真实闭环。
- 把采购、计划、售后中的关键页面从“可见”提升为“可执行”。
- 为平台接入、同步任务、失败队列、异常中心补齐人工处理与回放入口。
- 补齐关键经营指标和高层驾驶舱，让上线后的客户能看见系统价值。

### 8.2 P1 紧随其后

- 组织结构、审批中心、跨模块任务中心。
- 供应商货品档案、质量模板、质检追溯。
- 财务成本口径、费用规则、代销与税务扩展。
- 移动仓储执行和更完整的物流账单能力。

## 9. 菜单与页面关联评估

如果只看页面数量，本项目已经很多；如果看页面之间的业务关联，当前还有三类断层：

### 9.1 “有页面，无统一工作台”

很多页面已经建出来，但同一条业务链仍分散在不同菜单，导致用户无法从“一个工作台”完成完整任务。

典型例子：

- 销售订单、异常、发货、包裹、物流查询、售后、对账分散。
- 采购订单、到货、WMS 入库、财务应付尚未完全串起来。
- 售后、退货质检、退货入库、退款单据仍缺一条稳定导航链。

### 9.2 “有路由，有模块，但生产角色视角不够强”

目前更像开发视角的模块拆分，而不是仓库主管、审单员、客服主管、采购专员、财务会计的角色视角。

工业级 ERP 更适合以角色工作台补充导航：

- 审单员工作台。
- 仓库执行工作台。
- 采购执行工作台。
- 售后与客服工作台。
- 财务对账工作台。

### 9.3 “设置页多，产品主线弱”

项目中已经存在很多设置类页面，但它们还没有稳定地挂在对应业务域后面。继续扩展会导致设置越来越多、主业务越来越散。

## 10. 建议的上线时间判断

以下时间判断基于一个现实假设：

- 持续投入团队约 5 到 7 人。
- 其中至少有 2 名前端、2 名后端、1 名测试或兼 QA。
- 现有架构不推倒重来，只做产品化收口和关键闭环补强。

在这个假设下：

| 阶段 | 目标 | 估算周期 |
| --- | --- | --- |
| 阶段 A | 单商户试点版：补齐 P0 菜单重构、OMS/WMS/接入/财务轻闭环 | 8 到 12 周 |
| 阶段 B | 首个可收费商业版：补齐采购、计划、售后、报表、基础经营看板 | 4 到 6 个月 |
| 阶段 C | 工业化平台版：补齐多商户、多组织、质量、协同、强财务与移动执行 | 8 到 12 个月 |

如果团队人数更少，或中途继续扩展新模块而不做收口，上述周期还会继续拉长。

## 11. 结论

从代码体量、集成测试、OpenAPI 和页面覆盖来看，项目已经跨过“原型期”，进入“平台骨架已成形”的阶段。

但从工业级商业软件的标准来看，当前真正要做的不是继续横向铺页面，而是完成以下三件事：

- 把菜单和页面关系从“功能堆叠”重构为“产品信息架构”。
- 把采购、计划、售后、财务、报表这些辅助域补成真实闭环。
- 把多商户、多组织、审批协同、质量体系这几个结构性短板纳入中期版本路线。

只要沿着这条路线推进，本项目完全有机会从“宽骨架项目”进入“可收费、可复制交付的 ERP 产品”阶段；如果继续只追求页面数量，产品成熟度会被长期卡在中段。
