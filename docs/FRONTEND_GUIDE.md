# 前端开发与工作台规范

> 更新日期：2026-05-06  
> 本文合并原前端结构、UI 开发规范、Web 测试、打印桥接、ErpDataGrid 决策与订单工作台规范。

## 技术栈与目录

- 应用目录：`apps/erp-web`。
- 技术栈：Vite、React、TypeScript、Ant Design / Pro、Vitest、Playwright。
- 页面目录：`apps/erp-web/src/pages/`，按业务域组织。
- API 目录：`apps/erp-web/src/api/`，必须与 `openapi/erp_api_v1.yaml` 保持一致。
- 共享组件：`apps/erp-web/src/components/`，跨页面复用组件放在这里，业务域私有组件放在对应页面目录内。

## 页面建设原则

- 页面必须服务明确岗位和业务动作，不为补菜单而创建空页面。
- 核心页面优先使用工作台结构：快速筛选、主表、批量动作、明细联动、异常提示和审计入口。
- 状态、权限、错误提示和空状态必须与后端契约一致。
- 所有用户可见文案使用中文，业务术语保持统一。
- 需要长期维护的页面必须提供稳定 `data-testid`，方便 E2E 与回归测试。
- P0 页面必须在 `apps/erp-web/src/app/routeRegistry.ts` 标记为 `p0-ready`，且不得使用 `PlaceholderPage`；未上线页面只能标记为 `draft` 并从正式菜单隐藏。

## 工作台布局约定

核心业务页推荐采用以下布局：

1. 顶部区域：标题、状态概览、关键统计和全局动作。
2. 左侧区域：常用筛选、保存视图、快捷查询和异常分类。
3. 主表区域：业务对象列表、批量选择、批量动作、状态标识和关键列。
4. 右侧区域：当前对象详情、审核信息、履约信息、风险提示和操作日志。
5. 底部区域：子表、商品明细、物流轨迹、售后记录、财务差异和审计历史。

订单审核、订单查询、复核异常、渠道目录、商品下载、销售查询等页面应优先复用同一套工作台模式。

## 表格技术决策

订单工作台主表继续采用以下决策：

- AG Grid Community 兼容优先。
- Enterprise 只作为可选增强。
- `OrderWorkbenchMainGridEntry` 是订单审核、订单查询和复核异常等页面共享主表入口。
- 企业版能力只能作为渐进增强，不能成为基础功能、测试和上线门禁的硬依赖。
- 如果需要引入 Enterprise 能力，必须先提供 Community 降级方案和回归测试。

## 交互与状态

- 表格选择、焦点行、分页、筛选、保存视图和面板展开状态必须可恢复。
- 批量动作执行前必须显示影响范围，执行后必须反馈成功、失败和可重试项。
- 页面不能吞掉后端错误；权限不足、状态不允许、数据冲突和幂等冲突要给出清晰中文提示。
- 危险操作必须二次确认，并记录操作原因。

## 性能预算

- 首屏以真实接口和骨架屏为准，不用大量前端假数据掩盖接口缺口。
- 大表格必须考虑虚拟滚动、列裁剪、分页、后端过滤和批量操作性能。
- 工作台页面应避免在渲染路径中做大对象深拷贝或重复计算。
- 页面新增依赖前必须评估包体、许可、浏览器兼容性和替代方案。

## 测试规范

- 单元测试：纯函数、状态模型、表格列模型和权限判断优先使用 Vitest。
- 组件测试：复杂工作台交互需要覆盖筛选、选择、批量动作和状态恢复。
- E2E：关键业务链路使用 Playwright，至少覆盖登录、页面可达、主表加载、关键动作和错误提示。
- 回归测试：修复缺陷时优先补能复现问题的测试，不只修改实现。

## 打印桥接

- 打印模板、打印任务、设备令牌和任务完成回写统一走后端 API。
- 前端只负责创建、查询、预览和重试打印任务，不直接控制本地打印设备。
- 打印失败必须可见、可重试、可追踪到订单或出库单。

## 开发检查清单

- 页面是否对应 `docs/PRODUCT_SCOPE.md` 中的业务域和优先级。
- API 是否已同步到 OpenAPI，并生成或更新前端调用层。
- 权限、审计、错误提示、空状态和加载态是否齐全。
- 是否提供稳定测试标识和必要的回归测试。
- 是否避免创建新的重复布局、重复表格封装或重复状态模型。
