# ERP Web UI 开发统一规范

- 文档状态：`ACTIVE`
- 生效日期：`2026-04-16`
- 适用范围：`apps/erp-web/src/**`
- 目标对象：高频使用工作台的企业级电商 ERP 页面、组件、交互与 E2E 验收

## 1. 文档定位

本文件是后续 Web UI 开发的唯一主规范，用于统一：

1. 页面骨架与模板复用规则。
2. 主数据表、左侧筛选、右侧详情、底部子表的交互标准。
3. 批量操作、筛选、选择、排序、焦点、反馈、异常态等细节定义。
4. UI 回归测试、截图验证与文档维护方式。

本文件不是视觉灵感稿，也不是一次性方案预览稿。凡是会影响后续页面复用、用户学习成本、开发实现口径的内容，都必须在本文件落地。

## 2. 企业级电商 ERP UI 的设计目标

企业级电商 ERP 的主用户不是一次性访客，而是高频、长时段、目标明确的运营人员。UI 设计必须优先服务以下目标：

1. 高密度信息下可快速定位、筛选、批量处理。
2. 多页面之间交互习惯一致，降低培训与切换成本。
3. 长时间使用不疲劳，减少视觉噪音、误触和焦点丢失。
4. 所有关键动作都有明确反馈，避免“点了但不知道是否生效”。
5. 页面在 80% 的时间里围绕主数据表展开，其他模块必须服务主表，不得喧宾夺主。

## 3. 单一入口与关联文档

后续 UI 规范以本文件为唯一入口。涉及主表技术路线与工作台统一接入时，补充参考：

1. `docs/ErpDataGrid/order-workbench-technology-decision-2026-04-15.md`
2. `docs/web/TESTING.md`

禁止再新增并行“临时 UI 规划文档”“一次性模板说明文档”“交互预览稿”作为长期入口。

## 4. 技术基线

1. 前端框架：`React + TypeScript + Ant Design + AG Grid`
2. 主表策略：`AG Grid Community 兼容优先，Enterprise 仅作为可选增强`
3. 订单三页主表统一入口：`OrderWorkbenchMainGridEntry`
4. 工作台页面骨架统一模板：`WorkbenchMainTableTemplate`
5. 工具栏统一模板：`WorkbenchToolbarTemplate`

## 5. 模板治理规则

### 5.1 白名单模板（当前允许）

1. `WorkbenchMainTableTemplate`
2. `WorkbenchToolbarTemplate`
3. `UiModule05OrderReviewRightPanelTemplate`
4. `UiModule08OrderReviewLeftPanelTemplate`

### 5.2 禁止事项

1. 禁止为同语义页面新增别名模板，例如 A 调 B、B 调 C 的多级转发层。
2. 禁止将一次性页面私有布局抽成公共模板。
3. 禁止为了减少当前改动而增加中间组件层。
4. 禁止页面层绕开共享入口直接接多套主表实现。

### 5.3 新模板准入规则

新增模板必须同时满足：

1. 至少 2 个真实页面复用。
2. 提供对应 E2E 回归用例。
3. 提供迁移收益说明，至少覆盖以下一项：
   - 减少重复代码
   - 统一交互口径
   - 降低维护复杂度
   - 降低用户学习成本

## 6. 页面骨架标准

### 6.1 典型工作台结构

企业级电商 ERP 的标准工作台页面采用四区域结构：

1. 顶部工具栏：查询、批量动作、导出、帮助、诊断、视图切换。
2. 左侧模块：分类过滤、树形筛选、统计摘要、策略筛选。
3. 主数据表：主操作区，承载排序、选择、列筛选、右键菜单、分页与状态汇总。
4. 右侧详情与底部子表：展示当前焦点行的扩展信息，不抢主表主导地位。

### 6.2 信息主次关系

1. 主数据表始终是页面视觉与操作中心。
2. 左侧模块用于缩小范围，不用于替代主表。
3. 右侧面板用于查看与轻量修改，不承担大批量编辑主流程。
4. 底部子表用于补充上下文，不应破坏主表滚动与选择连续性。

### 6.3 桌面端尺寸基线

1. 左侧模块默认宽度：`220px`，允许在 `200-300px` 间调整。
2. 右侧面板默认宽度：`260px`，允许在 `240-320px` 间调整。
3. 底部子表默认高度：`240px`，允许在 `180-360px` 间调整。
4. 主数据表保底可用宽度：`980px`。

### 6.4 移动端与窄屏规则

1. 小于桌面宽度时，优先折叠右侧面板，其次折叠左侧模块。
2. 主数据表宽度不足时，不缩到不可读；应允许横向滚动。
3. 不在移动端强行保留桌面四栏并排布局。

## 7. 密度、节奏与视觉噪音控制

### 7.1 企业 ERP 密度基线

1. 主区块间距：`12px`
2. 紧凑区块内部间距：`8px`
3. 常规输入框高度：`28px`
4. 常规按钮高度：`28px`
5. 表头高度：`32px`
6. 表体行高：`30-32px`
7. 主内容字号：`12-13px`
8. 区块标题字号：`14-16px`

### 7.2 禁止事项

1. 禁止大面积空白卡片化展示高频操作页。
2. 禁止为了“看起来高级”牺牲信息密度。
3. 禁止在高频工作台页面使用夸张动画、长过渡和高饱和装饰背景。

## 8. 工具栏交互标准

### 8.1 工具栏分区

工具栏按职责分为三段：

1. 左侧：主动作与页面级开关，例如审核、复核、拆单、合单、批量修改。
2. 中部：页面标题或视图状态指示，仅在确有必要时显示。
3. 右侧：搜索、导出、打印、帮助、诊断等辅助能力。

### 8.2 排列顺序

1. 主动作在前，辅助动作在后。
2. 危险动作与高频动作之间必须有明确分隔。
3. 搜索输入框与搜索按钮必须相邻，避免跨区域跳跃。

### 8.3 搜索规则

1. 搜索框占位文案必须说明支持的关键字范围。
2. 按回车与点击“查询”必须等价。
3. 搜索执行后重置分页到第一页。
4. 搜索输入过程中不得无意触发整页刷新。

## 9. 左侧模块标准

### 9.1 左侧模块职责

左侧模块承担以下能力：

1. 分类缩小数据范围。
2. 展示当前口径的统计摘要。
3. 提供结构化筛选表单入口。

### 9.2 左侧过滤树规则

1. 节点点击应立即生效，不需要额外确认按钮。
2. 节点高亮必须稳定，切换分页或右侧详情时不能丢失。
3. 节点计数必须与当前口径一致，并明确“全部订单 / 待审核订单 / 待复核订单”等统计范围。
4. 树过滤搜索仅影响左侧节点可见性，不直接改写主表关键字搜索框内容。

### 9.3 左侧筛选表单规则

1. 左侧筛选表单负责结构化条件，例如时间、仓库、物流、区域、策略。
2. 点击“应用”后才写入主查询条件。
3. 点击“重置”必须恢复表单初始值并清空已应用条件。
4. 左侧筛选的已应用状态必须在标签页切换、详情查看后保持。

## 10. 主数据表标准

### 10.1 主数据表的定位

主数据表是企业级电商 ERP UI 的核心交互载体。所有页面细节定义必须优先围绕以下问题：

1. 用户能否快速看清当前数据范围。
2. 用户能否稳定地选中、定位、对比、批量处理。
3. 用户在刷新、切换页签、打开详情后是否会丢失上下文。

### 10.2 列定义标准

1. 常用主键列、状态列、平台列、店铺列、时间列放在靠前位置。
2. 数值列右对齐。
3. 状态与异常信息优先使用清晰文本或轻量徽标，不用过度图标化。
4. 列宽调整反馈以边框和拖拽行为为主，不保留冗余拖拽符号。

### 10.3 选择列标准

1. 选择列固定在最左。
2. 选择列宽度保持窄而稳定，不随页面各自漂移。
3. 头部全选框必须支持三态：未选、半选、全选。
4. 每一行复选框必须视觉居中、键盘可操作、命中范围清晰。

### 10.4 行焦点与激活态

1. 选中态与当前焦点行必须可区分，不能只用一种样式表示。
2. 鼠标单击行用于激活当前行。
3. 双击行用于打开详情或主动作，但必须在文档和实现里保持一致。
4. 刷新数据后应尽量恢复焦点行与滚动位置。

### 10.5 排序规则

1. 排序图标不得出现黑块、错位或遮挡。
2. 当前排序列与排序方向必须清晰可见。
3. 若页面只允许单列排序，则必须在文档与实现中保持一致。
4. 排序行为不能导致表头重排、焦点丢失或筛选控件闪烁。

### 10.6 滚动条与滚动容器

1. 同类工作台页面的底部滚动条样式必须统一。
2. 主表横向滚动条位置必须稳定，不能在不同页表现出不同层级的滚动容器。
3. 当底部子表可见时，滚动条与底栏的关系必须一致，不能有页面“有滚动条”、有页面“看不到滚动条”。

## 11. 列筛选与多来源筛选规则

### 11.1 列筛选强制规则

订单类主表必须满足：

1. 输入文本时，仅在回车后执行筛选。
2. 粘贴文本时，自动执行筛选。
3. 多标签页切换后，保留筛选输入值、钩选状态和已生效条件。
4. 输入过程中必须保持焦点，不得出现输入 1 个字符就刷新并失焦。

### 11.2 单列筛选约束

1. 同时只允许 1 列列筛选。
2. 选择第 2 列作为筛选目标时，必须自动取消前一列的列筛选。
3. UI 层必须明确当前正在筛选哪一列，避免用户误以为多列同时生效。

### 11.3 左侧过滤与列筛选叠加规则

1. 左侧模块进行过滤或筛选时，取消列筛选的生效结果。
2. 左侧过滤完成后，列筛选可以继续使用。
3. 不允许先列筛选，再叠加左侧过滤继续生效。
4. 筛选切换过程中，列筛选控件不能消失留空。

### 11.4 保存视图规则

保存视图至少包含：

1. 当前列筛选状态
2. 关键字搜索状态
3. 左侧筛选与左侧标签页状态
4. 需要时包含分页与列显示配置

## 12. 批量操作标准

### 12.1 基础要求

1. 批量动作必须明确说明“作用于当前选中”还是“作用于查询结果”。
2. 按钮禁用态必须清晰，不允许用户在无数据或无权限时误点。
3. 批量动作执行前必须校验关键前置条件，例如物流为空、无效货品、权限不足。

### 12.2 反馈要求

1. 执行成功后必须返回明确条数或对象数。
2. 执行失败时必须说明失败原因，不允许笼统提示“操作失败”。
3. 若动作为部分成功，必须明确成功数与失败数。

### 12.3 危险动作要求

1. 合单、拆单、强制审核、批量修改等带业务风险的动作必须有更强反馈。
2. 危险动作优先放在主动作组中靠后位置，并与普通动作视觉分组。

## 13. 右侧详情与底部子表标准

### 13.1 右侧详情面板

1. 右侧面板负责展示当前焦点行详情与轻量快捷修改。
2. 面板内容切换时不能闪屏、空白或跳回顶部。
3. 快捷修改字段必须即时反馈保存中状态与结果。

### 13.2 底部子表

1. 底部子表用于货品、日志、包裹、赠品策略等扩展信息。
2. 当前焦点行切换后，子表应自动刷新到对应数据。
3. 底部子表标签顺序在同类页面间必须一致。
4. 子表为空时要有清晰空态，而不是空白面板。

## 14. 状态反馈标准

### 14.1 加载态

1. 页面主加载要明确显示“加载中”或耗时信息。
2. 加载耗时在订单审核、订单复核、订单查询等同类页面中口径一致。
3. 局部刷新优先局部 loading，不允许每次小操作都整页闪烁。

### 14.2 空态

1. 空态要说明“没有数据”还是“当前筛选条件下没有结果”。
2. 空态优先提供可恢复动作，例如清空筛选、返回默认视图、重试。

### 14.3 错误态

1. 错误态要提供“失败原因 + 重试入口”。
2. 错误不能直接吃掉；日志、控制台和 UI 至少一处应保留定位线索。

### 14.4 成功反馈

1. 成功反馈简洁、明确、可量化。
2. 长耗时操作完成后必须有完成提示，不允许“结束但用户无感知”。

## 15. 焦点、键盘与可访问性标准

### 15.1 焦点可见性

1. 所有交互控件都必须有可见焦点。
2. 禁止全局 `outline: none`。
3. 必须使用 `:focus-visible` 或等价方案恢复焦点反馈。

### 15.2 icon-only 按钮

1. 所有 `icon-only` 按钮必须有 `aria-label`。
2. `aria-label` 必须是动作语义，不是图标名称。
3. 相同动作在不同页面上命名要一致，例如“刷新”“查询”“帮助”“诊断”。

### 15.3 键盘行为

1. 输入框输入期间，非必要快捷键不得抢占焦点。
2. 表格选中、复选框切换、回车查询等行为必须可用键盘完成。
3. Esc、Enter、Tab 的行为在同类页面中应一致，不得一页生效、一页无效。

## 16. 诊断与开发期开关

1. 诊断功能允许在开发期间显示。
2. 发布版本必须默认关闭诊断入口。
3. 诊断开关必须集中治理，不允许各页面各自实现一套显隐规则。

## 17. 性能与工程约束

1. 优先修改现有代码，避免通过叠加新层规避重构。
2. 独立请求使用 `Promise.all` 并行发起，避免瀑布。
3. 大表格交互禁止明显重绘抖动。
4. 排序、筛选、分页、切换标签页时，优先保持焦点、滚动位置和已选状态。
5. 页面实现应尽量收敛到共享入口、共享 Hook 与共享模板，不把同类逻辑散落到页面层复制。

## 18. 反模式清单

以下情况视为 UI 工程反模式，应优先修复而不是继续扩展：

1. 同类页面底部滚动条样式不同。
2. 列筛选输入 1 个字符就触发刷新并失焦。
3. 主数据表选择列、排序图标、行高、分页区在不同页表现不一致。
4. 同一动作在不同页面文案不同、位置不同、反馈不同。
5. 页面通过新增模板壳层来掩盖结构混乱。
6. 开发诊断按钮直接暴露到生产。

## 19. UI 回归与发布门禁

每次涉及 UI 交互、模板、主表行为、左侧模块或批量操作的改动，至少执行：

1. `pnpm typecheck`
2. 订单列筛选回归：
   - `pnpm playwright test e2e/orders.spec.ts -g "orders column filter"`
3. 主表可见性与布局回归：
   - `pnpm playwright test e2e/workbench-main-table-visibility.spec.ts`
4. 左侧模块交互回归：
   - `pnpm playwright test e2e/order-review-left-panel-regression.spec.ts`

如包含下列改动，还应补充专项回归：

1. 排序与表头：补表头排序与排序图标回归
2. 滚动条与主表结构：补首屏截图与滚动条截图
3. 批量操作：补成功、失败、禁用态回归
4. 保存视图：补标签页切换后状态保持回归

如果包含交互改造，还需保留关键截图证据：

1. 首屏默认态
2. 筛选生效态
3. 左侧过滤生效态
4. 批量操作完成态
5. 异常或空态

## 20. 文档维护规则

1. UI 行为变更后，先更新本规范，再提交代码。
2. 技术路线调整必须同步更新技术决策文档。
3. 废弃的临时规划文档应直接删除，不保留为并行入口。
4. 新页面如要偏离本规范，必须在文档中写明偏离原因与适用范围。

## 21. 开发者自检清单

1. 是否复用了白名单模板？
2. 是否新增了不必要的中间模板层？
3. 是否补齐了所有 icon-only 按钮的 `aria-label`？
4. 是否保持了列筛选“回车执行、粘贴自动执行、切页保持”的规则？
5. 是否保证了左侧筛选与列筛选的叠加规则？
6. 是否保证了选择列、排序图标、底部滚动条的一致性？
7. 是否补充了对应的 E2E 回归？
8. 是否同步更新了本规范中的相关条目？
