# 后端服务与接口边界

> 范围：`crates/*`、`openapi/*`

本文面向接手后端或前后端联调的开发者，帮助快速理解：

- 运行中的几个核心服务分别负责什么
- 事件链路如何组织
- `erp-api` 的接口边界有多宽
- 应该从哪些文件开始读

## 1. Rust workspace 的层次

当前 workspace 可以粗分为四层：

### 1.1 基础与领域层

- `erp-common`
- `erp-types`
- `erp-domain`
- `erp-adapter`
- `erp-repo`
- `erp-outbox`

这层负责：

- 公共工具和类型
- 领域模型
- 仓储访问
- 事件/outbox 相关能力
- 适配器共性接口

### 1.2 平台适配层

- `adapter-taobao`
- `adapter-jd`
- `adapter-pdd`
- `adapter-douyin`

这层对应平台侧的接入适配逻辑，适合在处理签名、字段映射、平台任务时进入。

### 1.3 运行时服务层

- `erp-api`
- `erp-channel`
- `erp-dispatcher`
- `erp-worker`
- `erp-print-agent`
- `erp-analytics`

这是日常联调和运行时最常接触的一层。

## 2. 核心运行链路

从当前代码和文档能确认的主链路是：

```text
平台回调/同步任务
  -> erp-channel
  -> inbox / outbox
  -> erp-dispatcher
  -> NATS
  -> erp-worker
  -> 业务投影/异步任务
  -> erp-api / erp-web 对外查询与操作
```

更具体一点：

1. `erp-channel`
   接收入站 webhook，请求落库、去重、生成 inbox/outbox 事件

2. `erp-dispatcher`
   扫描 outbox，把事件发布到 NATS

3. `erp-worker`
   订阅事件并执行异步业务处理，如订单投影、导入导出、重试与清理作业

4. `erp-api`
   提供查询、操作、系统配置、权限、工作台、打印、报表等同步接口

## 3. 各核心服务的职责

### 3.1 `erp-api`

这是当前最重的服务入口，承担：

- 租户级业务接口
- 后台管理接口
- 报表与导出接口
- 权限与审计接口
- 系统配置与集成接口
- 工作台相关的查询与动作接口

阅读入口建议从：

- `crates/erp-api/src/router.rs`
- `crates/erp-api/src/app_state.rs`
- `crates/erp-api/src/orders/`
- `crates/erp-api/src/sales_orders.rs`
- `crates/erp-api/src/planning.rs`

开始。

### 3.2 `erp-channel`

关注点是平台入站事件：

- webhook 接收
- 签名/鉴权
- 原始 payload 落库
- 去重与入站事件记录

适合处理“平台为什么没进系统”“回调为什么重复/乱序”这类问题。

### 3.3 `erp-dispatcher`

关注点是数据库 outbox 到消息总线的投递。  
适合处理“事件是否发出”“消息是否卡在 outbox”这类问题。

### 3.4 `erp-worker`

关注点是消费与异步任务执行，包括：

- 事件处理
- token 刷新
- 导出任务
- 售后导入任务
- 清理类作业
- DLQ / 重放相关能力

适合处理“为什么数据已入站但业务没更新”“异步任务为何失败”这类问题。

## 4. `erp-api` 的接口边界

`crates/erp-api/src/router.rs` 已经非常宽，当前能直接看到的接口组织大致包括：

- `healthz`、登录、当前用户资料
- 报表与统计
- 导出任务
- 打印代理接口
- 租户级业务接口 `/v1/tenants/:tenant_id/*`
- 后台管理接口 `/admin/*`

租户级接口已经覆盖的主要业务域包括：

- 订单、审核、复核、结算、履约
- 销售订单与销售店铺配置
- 渠道、店铺、平台同步、字段映射
- WMS 出库、入库、波次、拣货、补货、月台、作业配置
- 库存、冻结、盘点、调拨、移动、同步任务
- 商品、SKU、条码、单位、包装、生命周期、可售范围
- 采购、收货、退货、建议与计划
- 售后、逆向、质检、拦截、SLA、导入任务
- 物流、运单、承运、运费、履约异常
- 财务、应收应付、费用、成本、税务、利润
- 打印设备、模板、映射、打印任务
- 权限、角色、用户、数据权限、审计日志
- 系统工作流、集成、自定义字段、审计报表
- 失败队列、outbox、前端路由诊断、同步任务、操作日志

接手后端时，可以先把它理解成：

- 一个以 `erp-repo` 为底座的“租户级 ERP 聚合 API”

## 5. 仓储层的价值

`crates/erp-repo/src/` 是理解真实业务覆盖范围最直接的地方之一。  
从模块名可以直接看到当前仓储层已经覆盖的业务域，例如：

- orders / sales_orders / order_reviews / fulfillment
- wms / inbounds / stock_counts / stock_transfers / stock_moves
- products / skus / product_categories / product_barcodes
- procurement / suppliers
- after_sales / after_sale_cases / after_sales_inspections
- finance_* / reports
- channels / shops / mapping_rules / sync_jobs
- permissions / rbac / audit_logs / data_scopes
- print_* / shipment_* / logistics_*

如果你在判断“这个域到底只是前端占位，还是后端和数据层也已经铺了”，仓储层通常能给出更可靠的答案。

## 6. OpenAPI 与前端联动

仓库根目录和前端目录都把 OpenAPI 作为前后端契约的关键中介：

- 主契约文件：`openapi/erp_api_v1.yaml`
- 前端生成命令：`pnpm --dir apps/erp-web run generate:api`

因此接手接口问题时，建议总是把这四层串起来看：

1. `openapi/erp_api_v1.yaml`
2. `crates/erp-api/src/router.rs` 与对应 handler
3. `crates/erp-repo/src/*`
4. `apps/erp-web/src/api/*`

## 7. 建议从哪里开始读

### 7.1 想快速理解服务边界

先读：

1. `README.md`
2. `docs/spec/01_architecture.md`
3. `crates/erp-api/src/router.rs`
4. `crates/erp-channel/src/main.rs`
5. `crates/erp-dispatcher/src/main.rs`
6. `crates/erp-worker/src/main.rs`

### 7.2 想接某个业务域

建议顺序：

1. 先在 `crates/erp-repo/src/` 找同名模块
2. 再找 `crates/erp-api/src/` 中的路由与 handler
3. 再回看对应迁移和 OpenAPI
4. 最后联动前端页面与 API 封装

## 8. 当前后端最重要的接手结论

1. 后端已经不是单一“订单闭环”骨架，而是一个业务域非常宽的 ERP 聚合后端。
2. `erp-api` 承担了极大的接口聚合职责，是接手后端的第一入口。
3. 事件链路的定位很清楚：入站在 `channel`，投递在 `dispatcher`，消费在 `worker`，查询与操作在 `api`。
4. 判断某个业务域是否真实落地，优先看 `erp-repo`、迁移脚本和 OpenAPI，而不是只看文档标题。
