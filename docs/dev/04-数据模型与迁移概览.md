# 数据模型与迁移概览

> 范围：`migrations/`、`docs/spec/*schema*.md`、`crates/erp-repo/src/*`

本文面向接手数据库、接口联调或领域建模的开发者，帮助快速理解：

- 迁移文件整体体现了哪些业务域
- 数据模型大概经历了哪些扩展阶段
- 改数据模型时应该同步检查哪些地方

## 1. 当前迁移规模

截至 2026-04-25，`migrations/` 下可以看到 `102` 个 SQL 迁移文件。  
这些迁移已经不只是初始化骨架，而是覆盖了相当多的 ERP 业务域。

从命名可以明显看出，迁移已覆盖：

- 订单与订单审核
- 售后与逆向
- 商品、SKU、条码、单位、包装
- 库存、盘点、调拨、移动、冻结
- WMS 入库、出库、波次、扫描、质检
- 采购、供应商、采购管理
- 财务、对账、利润、税务、费用
- 平台接入、店铺配置、同步作业
- 打印、物流、运单、承运
- 权限、审计、系统配置、特性开关
- 报表、导出、前端路由诊断

## 2. 看迁移时要注意的一点

迁移文件名前缀整体上按阶段递增，但并不是每个数字前缀都严格唯一。  
当前仓库里可以直接看到一些重复前缀，例如：

- `0060_*`
- `0073_*`
- `0074_*`
- `0079_*`
- `0095_*`

接手时不要只按“数字编号”理解先后，应该按完整文件名顺序和实际内容一起判断。

## 3. 迁移阶段的粗分

下面的分段不是权威发布里程碑，而是为了帮助接手时更快建立结构感。

### 3.1 基础骨架期

大致对应：

- `0001_init.sql`
- `0002` 到 `0018`

主要建立：

- 初始订单、售后、商品、库存、打印、运单基础表
- Inbox / dedup / idempotency / dead letter 等可靠性骨架
- feature flags、操作日志、默认设置等基础治理能力

### 3.2 核心业务域铺开期

大致对应：

- `0019` 到 `0038`

主要新增：

- 目录类数据
- OMS 订单审核
- WMS 入库、出库
- 履约与采购
- 平台接入
- 系统管理
- 财务对账
- 库存同步
- 打印与报表导出

### 3.3 管理能力扩展期

大致对应：

- `0039` 到 `0059`

主要新增：

- 权限目录与角色体系
- waybill、shipment push、print device token
- after-sales import
- 客户、供应商、目录增强
- 商品中心和仓储策略
- sync job runs

### 3.4 工业化能力增强期

大致对应：

- `0060` 到 `0081`

主要新增：

- 盘点差异、包装校验、入库质检
- 渠道字段映射、订单标签
- 物流匹配规则
- SKU 批次与序列号策略
- 店铺商品下载
- 营销、采购管理、物流履约
- 商品主数据治理
- 财务管理
- 扩展订单字段、全局状态、订单状态体系

### 3.5 工作台与治理加固期

大致对应：

- `0082` 到 `0095*`

主要新增：

- 默认物流与修复
- 扫描、质检、冻结审批
- 订单状态日志
- 销售订单
- CRM / 统计 API
- 结算工作台
- ATP 与主数据治理
- 订单链路增强
- 前端路由诊断索引
- 订单匹配/发货/波次动作守卫
- 工作流引擎
- 多商家组织基线

## 4. 可以把数据模型按哪些业务簇来理解

### 4.1 订单与事件链路

关键关注点：

- webhook 入站
- inbox/outbox
- orders / order_items
- 审核、复核、异常、状态历史

这是系统主线，也是很多异步处理和前端工作台的上游。

### 4.2 商品与主数据

关键关注点：

- products
- skus
- product categories / brands / units
- barcodes / packaging / lifecycle
- channel availability / warehouse bindings

这块是库存、采购、销售和店铺商品处理的共同基础。

### 4.3 库存与 WMS

关键关注点：

- inventory balances / ledgers / costs
- freezes / approvals
- stock counts / moves / transfers
- inbounds / outbounds / waves / pick tasks
- scan / QC / workflow configs

这是仓储、履约和作业执行相关变更最集中的区域。

### 4.4 渠道、店铺与同步

关键关注点：

- shops / channels
- shop auth / token / sync settings
- sync jobs / sync job runs
- field mappings / channel sku mappings / mapping rules
- shop product download / match / parse

这块把平台侧能力和内部主数据联了起来。

### 4.5 售后、采购、财务、打印与系统治理

这些域已经明显有独立模型与迁移，不再只是“预留占位”：

- after-sales / after-sale cases / inspections / reasons
- procurement / suppliers / receipts / returns
- ar / ap / expenses / costing / tax / profit
- print devices / mappings / templates / jobs
- permissions / roles / users / data scopes / audit logs / settings

## 5. 改数据模型时建议同步检查的四层

如果要修改某个业务域的数据结构，建议至少同步检查：

1. `migrations/` 中最新相关迁移
2. `crates/erp-repo/src/` 对应仓储模块
3. `crates/erp-api/src/` 对应接口与 DTO
4. `openapi/erp_api_v1.yaml` 与前端 `src/api/*`

只改其中一层，通常会留下契约漂移或前后端认知不一致的问题。

## 6. 文档与代码的对应关系

理解数据模型时，可以把几类资料这样对照着看：

- 真实表结构与演进：`migrations/`
- 领域结构说明：`docs/spec/*schema*.md`
- 业务流程对模型的使用方式：`docs/spec/*workflow*.md`
- 真实读写代码：`crates/erp-repo/src/*`
- 对外接口契约：`openapi/erp_api_v1.yaml`

其中真正的“落地事实”仍然以迁移和代码为准。

## 7. 当前最重要的接手结论

1. 数据模型覆盖面已经很广，不能再把仓库理解成只有订单主链路的原型。
2. 迁移文件能最直接反映业务域是否真实落地，很多域在前端完全开放前就已经有表结构和仓储实现。
3. 迁移前缀编号存在重复，读迁移时应按完整文件名和上下文判断，而不是只看数字。
