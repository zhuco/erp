# 项目总览与阅读路径

> 更新时间：2026-04-25  
> 目标读者：第一次接手本仓库的开发、维护、联调人员

本文不是新的产品规格文档，也不替代 `docs/spec/`、`docs/ops/` 和真实代码。它只回答三个问题：

1. 这个项目当前到底是什么形态？
2. 仓库里的主要代码和文档分别放在哪？
3. 接手时应该按什么顺序阅读？

## 1. 一句话看项目

这是一个面向多平台电商场景的 ERP monorepo，仓库同时包含：

- Rust 后端服务与领域仓储
- React/Vite Web 前端
- PostgreSQL 迁移脚本
- OpenAPI 契约
- 本地联调、部署和发布文档

项目主线仍然围绕订单、履约、库存、售后、渠道接入与系统治理展开，但代码覆盖范围已经明显超出“最小订单闭环”，包含商品、采购、财务、营销、报表、打印、权限等多个业务域。

## 2. 当前代码现状

截至 2026-04-25，仓库里可以直接看到的结构规模大致如下：

- Rust workspace 下有 `16` 个 crate
- `migrations/` 下有 `102` 个 SQL 迁移文件
- `apps/erp-web/src/pages/` 下有约 `359` 个页面或占位页面文件
- `apps/erp-web/src/app/router.tsx` 当前主路由实际挂载的是一组相对收敛的页面入口，而不是全部页面文件

这意味着接手时要特别注意一件事：

- “代码覆盖范围” 和 “当前主入口开放范围” 不是一回事

仓库中已经铺开了大量领域页面、接口与数据模型，但前端主导航当前主要聚焦在渠道目录、销售工作台和销售设置等核心入口。看到大量页面文件并不代表这些页面都已经对外开放或进入稳定路径。

## 3. 仓库结构速览

| 路径 | 作用 |
| --- | --- |
| `apps/erp-web` | Web 前端，使用 React + Vite，包含页面、工作台模板、API 客户端、Mock、单测与 E2E |
| `crates/erp-api` | 主 API 服务，聚合大多数租户级和后台管理接口 |
| `crates/erp-channel` | Webhook 入站服务，承接平台回调并写入入站事件 |
| `crates/erp-dispatcher` | Outbox 事件分发器，把数据库中的事件投递到 NATS |
| `crates/erp-worker` | 事件消费和异步任务执行入口 |
| `crates/erp-repo` | 数据访问层，按业务域拆分了大量仓储模块 |
| `crates/erp-domain` / `crates/erp-types` / `crates/erp-common` | 领域模型、通用类型和公共基础能力 |
| `crates/adapter-*` | 平台适配器骨架，当前可见淘宝、京东、拼多多、抖音 |
| `migrations` | PostgreSQL 迁移脚本，是理解数据模型演进最直接的入口 |
| `openapi` | API 契约；前端生成的类型与客户端以此为基础 |
| `infra` / `docker-compose*.yml` | 本地依赖、SSO、可观测性等基础设施编排 |
| `docs/spec` | 产品蓝图、流程、数据结构和接口约束文档 |
| `docs/ops` | 发布门禁、运行手册、运维与质量流程 |
| `docs/dev` | 面向开发与联调的说明文档 |
| `docs/reports` | 阶段性报告与评估；历史报告已归档 |
| `docs/superpowers` | 设计、方案、实施计划的过程留痕，不应替代当前权威规格 |

### 4.4 命令统一入口

项目已经明确把根目录 `package.json` scripts 作为统一命令入口，常用命令包括：

```bash
pnpm run repo:verify
pnpm run accept:web
pnpm run accept:backend
pnpm run accept:all
```

本地前后端联调方式见 `docs/dev/前后端使用方式.md`。

## 6. 这组开发文档怎么用

本次补充的开发文档组分工如下：

- `01-项目总览与阅读路径`：入口文档，帮助快速建立全局认识
- `02-前端结构与路由现状`：解释 Web UI 的分层、模板体系与主路由现状
- `03-后端服务与接口边界`：解释服务职责、事件链路和 API 覆盖范围
- `04-数据模型与迁移概览`：解释迁移分段和数据模型观察点

它们都属于“接手导航文档”，不负责定义产品真相。发生冲突时，仍然按以下顺序裁决：

1. 真实代码
2. OpenAPI 与迁移脚本
3. `docs/spec` 和 `docs/ops` 中的权威文档
4. 本组开发接手文档

## 7. 接手时最值得先确认的几个事实

1. 当前主路由开放的页面比 `src/pages` 中的页面文件少得多，不要仅凭页面目录判断可用范围。
2. 后端 API 的领域覆盖面已经很宽，很多域先有后端和数据层，再逐步挂到前端主导航。
3. 仓库内同时存在规格文档、评估报告、实施计划和开发说明，阅读时要分清“权威规格”和“过程留痕”。
4. `docs/list.md` 已经定义了文档裁决层级；整理或新增文档时，应优先补充入口，不要再平行复制一份总纲。
