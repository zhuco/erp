# Codex 多 AI 并行开发与工业级交付手册（目标评分 4.5+）

> 适用场景：一个人同时驱动多个 AI 会话、多个分支、多个工作区并行开发，并要求结果可合并、可回滚、可审计、可持续迭代。  
> 当前版本：v3.0  
> 更新日期：2026-04-14  
> 适配仓库：`F:/erp`

## 0. 文档定位

这不是一份“如何多开几个 AI”的经验贴，而是一份可执行的工程操作手册。

它要解决的核心问题只有一个：

**当一个人同时操作多个 AI 做工业级 ERP 开发时，怎样避免互相踩代码、怎样保证每次合并都有证据、怎样把项目稳定推进到 `4.5 / 5` 以上。**

本手册默认服务于以下目标：

1. 当前项目继续向工业级电商 ERP 收敛。
2. 售后、退换货、补发货、平台售后联动是重点业务域。
3. 开发主体是“一个人 + 多个 AI 会话”，不是传统多人团队。
4. 交付要求不是演示可跑，而是可收费、可试点、可持续上线。

## 1. 使用范围与边界

### 1.1 适用范围

本手册适用于以下场景：

1. 同时存在多个 AI 会话并行改代码。
2. 同时存在多个功能任务并行推进。
3. 同时存在前端、后端、OpenAPI、数据库、测试、文档联动改动。
4. 需要在脏工作区、长周期迭代中尽量降低合并风险。

### 1.2 不在本手册内的内容

以下内容不作为本手册主体：

1. 单一功能页面的 UI 细节。

3. 组织人事管理和外部团队协作制度。
4. 商业合同、报价、售前方案文本。

这些内容应分别落在需求文档、设计文档、规格说明和交付计划中。

### 1.3 与仓库内其他文档的关系

## 2. 4.5+ 的统一定义

“4.5+”不能只靠感觉判断，必须可量化、可追溯、可复盘。

### 2.1 总分模型

总分满分 5.0，采用 6 个维度加权：

| 维度 | 权重 | 目标分 |
| --- | --- | --- |
| 并行隔离 | 15% | `>= 4.7` |
| 代码与测试 | 25% | `>= 4.6` |
| 合并治理 | 20% | `>= 4.5` |
| 可观测与审计 | 15% | `>= 4.4` |
| 交付效率 | 15% | `>= 4.3` |
| 稳定性 | 10% | `>= 4.6` |

计算公式：

```text
总分 = Σ(维度得分 × 权重)
```

最终达标条件不是只有“总分 >= 4.5”，还必须同时满足：

1. 任一单维不能低于 `4.2`。
2. 不能触发本手册第 2.4 节的封顶/封底规则。
3. 近 2 周不能出现 P0 回归。
4. 关键门禁必须保持真实生效，不能通过“跳过测试”伪达标。

### 2.2 六大维度详细评分口径

#### A. 并行隔离（15%）

| 分数 | 判定标准 |
| --- | --- |
| 5.0 | 100% 任务使用独立分支和独立工作区，无 `main` 直改，无重复写同一分支 |
| 4.5 | 偶发共享文件串行处理，但有记录、有锁、有回归 |
| 4.0 | 出现少量越界改动，但被及时发现并修复 |
| 3.5 以下 | 有多个 AI 改同一分支、同一文件冲突频发、边界失控 |

#### B. 代码与测试（25%）

| 分数 | 判定标准 |
| --- | --- |
| 5.0 | P0/P1 变更都有单测/集成/E2E 或等价回归覆盖，关键链路通过率 `>= 99%` |
| 4.5 | 高风险链路具备自动化测试，个别低风险改动仍需补测 |
| 4.0 | 测试存在空白区，但主链路无明显失守 |
| 3.5 以下 | 依赖手工验证，或大量“先合并再补测试” |

#### C. 合并治理（20%）

| 分数 | 判定标准 |
| --- | --- |
| 5.0 | 每次合并都有任务卡、测试证据、回滚点、风险说明 |
| 4.5 | 大部分合并完整执行门禁，少量低风险文档改动从简 |
| 4.0 | 门禁执行不稳定，偶发无证据合并 |
| 3.5 以下 | 依赖口头判断，回滚路径不清晰 |

#### D. 可观测与审计（15%）

| 分数 | 判定标准 |
| --- | --- |
| 5.0 | 关键写操作同时具备指标、日志、审计和落库证据 |
| 4.5 | 主链路闭环完整，次级链路仍有少量盲区 |
| 4.0 | 指标或审计覆盖不完整，但尚可定位主要问题 |
| 3.5 以下 | 问题发生后无法快速回答“发生了什么、影响了谁” |

#### E. 交付效率（15%）

| 分数 | 判定标准 |
| --- | --- |
| 5.0 | lead time、返工率、冲突率均稳定下降，集成窗口节奏固定 |
| 4.5 | 效率总体稳定，偶发阻塞但能当天排除 |
| 4.0 | 任务切换频繁，集成经常延期 |
| 3.5 以下 | 大量时间消耗在冲突、返工、补救合并 |

#### F. 稳定性（10%）

| 分数 | 判定标准 |
| --- | --- |
| 5.0 | 近 2 周无 P0/P1 回归 |
| 4.5 | 无 P0，P1 能在 SLO 窗口内闭环 |
| 4.0 | 偶发 P1 回归，但有明确根因和修复机制 |
| 3.5 以下 | 回归频发，版本质量波动大 |

### 2.3 周评分与日评分如何使用

建议同时维护两种分数：

1. 日评分：每天收工前记录一次，用于调整次日任务优先级。
2. 周评分：每周固定时间汇总，用于判断是否真正进入 `4.5+` 区间。

推荐算法：

```text
周总分 = 日评分平均值 × 70% + 周发布演练分 × 30%
```

只有当连续 2 周周总分都 `>= 4.5`，并且没有触发硬性封顶规则时，才认定“达到工业级并行交付水平”。

### 2.4 封顶 / 封底规则

以下情况一旦出现，总分必须强制封顶或封底，防止“表面分高、真实失控”：

1. 出现 `main` 直接开发：
   总分封顶 `4.2`。
2. 出现“接口成功但无落库/无审计”：
   总分封顶 `3.9`。
3. 关键测试通过依赖 `skipping ... DATABASE_URL` 或 `pool timed out`：
   总分封顶 `4.0`。
4. 无法给出清晰回滚方案：
   合并治理单维封顶 `3.8`。
5. 两个 AI 同时改同一分支：
   并行隔离单维封顶 `3.5`。
6. 共享文件冲突通过“删除逻辑以过编译”解决：
   代码与测试单维封底 `3.0`。

## 3. 单人多 AI 的标准作业模型

### 3.1 角色模型

即使只有一个人操作，也必须把职责分清楚，否则很快会退化成“多个 AI 一起制造混乱”。

| 角色 | 责任 | 是否可兼任 |
| --- | --- | --- |
| Integrator（主控会话） | 拆任务、定边界、验门禁、做最终合并 | 是 |
| Worker（执行会话） | 按任务卡改代码并提交证据 | 否 |
| Reviewer（审查会话） | 专看风险、测试、回归和遗漏 | 是 |
| Release Guard（门禁会话） | 复核 OpenAPI、构建、E2E、发布清单 | 是 |
| Recorder（记录者） | 更新文档、评分卡、风险表 | 是 |

推荐最小配置：

1. 1 个主控会话。
2. 2 到 4 个执行会话。
3. 1 个审查/门禁会话。

### 3.2 为什么一个人操作多个 AI 也必须分支化

原因不是“流程好看”，而是为了避免以下现实问题：

1. 不同 AI 会在不同时间点给出不同假设，混在一个工作区很难分辨谁改了什么。
2. 同一上下文里叠加多个未完成任务，会让回滚和定位问题几乎不可行。
3. 当一个 AI 的思路走偏时，没有独立分支就无法安全放弃。
4. 多个工作区可以同时保留不同链路的编译与测试现场，便于快速切换。

一句话总结：

**分支不是为了团队流程，而是为了给单人多 AI 场景提供最小可控边界。**

### 3.3 标准工作流

完整流程如下：

1. 主控会话先评估当前目标，拆成 2 到 5 个并行子任务。
2. 每个子任务生成独立任务卡，指定白名单文件。
3. 每个子任务在独立分支和独立工作区执行。
4. 子任务提交时必须附带测试结果和风险说明。
5. 审查会话只看差异、风险和遗漏，不参与实现。
6. 主控会话按合并顺序执行门禁、集成和回归。
7. 每日收工前更新评分卡和风险表。

## 4. 任务拆分原则

### 4.1 适合并行的拆分方式

优先按以下维度拆分：

1. 按业务域拆分：
   例如售后状态机、售后财务对账、平台联动、客服工作台。
2. 按技术层拆分：
   例如后端持久化、OpenAPI 契约、前端工作台、E2E 门禁。
3. 按依赖方向拆分：
   先基础层，再业务层，再表现层。
4. 按风险类型拆分：
   把“高风险数据一致性”与“低风险文档/样式”分开。

### 4.2 必须串行的内容

以下高冲突资源默认不允许并行直接修改：

1. `crates/erp-api/src/lib.rs`
2. `crates/erp-repo/src/lib.rs`
3. `openapi/erp_api_v1.yaml`
4. `apps/erp-web/src/app/router.tsx`
5. `apps/erp-web/src/app/layout/menu.tsx`
6. `migrations/*.sql`
7. `scripts/release_gate_backend.mjs`
8. `scripts/verify_openapi_gate_v2.mjs`

这些文件必须采用“共享文件锁”机制：

1. 一次只允许一个任务持有编辑权。
2. 编辑前在任务卡中显式登记。
3. 合并前必须补跑受影响链路测试。

### 4.3 不应拆分的错误方式

以下拆法会显著提高失败率，应尽量避免：

1. 按页面一人、按 API 一人，但两边同时改同一协议。
2. 让两个 AI 同时改同一个模块，靠后期手工拼接。
3. 把“状态机”和“幂等”拆给不同 AI，但共用同一组 repo 文件。
4. 在未锁定 OpenAPI 和数据库迁移前，先让多个任务并行依赖它们。

## 5. 分支与工作区规范

### 5.1 命名规范

建议统一使用以下命名：

1. 分支：`codex/<domain>-<scope>-<yyyymmdd>`
2. 工作区：`../erp-<domain>-<scope>`

示例：

```powershell
git checkout -b codex/aftersales-finance-20260414
git worktree add ../erp-aftersales-finance codex/aftersales-finance-20260414
```

### 5.2 强制规则

1. 禁止两个 AI 写同一分支。
2. 禁止在 `main` 直接开发。
3. 禁止任务外顺手修文件。
4. 禁止合并前保留未识别的脏改动。
5. 禁止跨工作区复制未验证代码后直接提交。

### 5.3 工作区最小检查

每次开始工作前至少确认：

```powershell
git status --short
git branch --show-current
git rev-parse --show-toplevel
```

目标是保证：

1. 当前分支正确。
2. 工作区没有误带上其他任务的脏改动。
3. 根目录就是目标仓库，不是在错误 worktree 中操作。

## 6. Codex 子任务协议

本节是“支持子任务”的核心。无论你使用 Codex 子任务、多个桌面线程，还是多个外部 AI，会话之间都建议遵循同一协议。

### 6.1 子任务卡模板

每个 AI 接手任务前，都必须收到如下结构的任务卡：

```text
任务名：
目标：
业务背景：
允许修改文件：
- path A
- path B
禁止修改文件：
- path C
- path D
依赖前提：
完成定义（DoD）：
必须执行测试：
- command 1
- command 2
提交格式：
- commit hash
- 变更摘要
- 测试结果
- 残余风险
```

### 6.2 子任务提示词模板（执行会话）

以下模板可直接下发给 AI：

```text
你负责一个受边界约束的子任务，请只在白名单范围内修改。

任务目标：
<一句话目标>

业务背景：
<为什么做这件事>

允许修改文件：
<白名单>

禁止修改文件：
<禁区>

完成定义：
1. <DoD 1>
2. <DoD 2>

必须执行测试：
1. <command 1>
2. <command 2>

交付时只返回：
1. commit hash
2. 变更摘要
3. 测试结果
4. 残余风险

不要扩展范围，不要顺手改动非目标模块。
```

### 6.3 子任务提示词模板（审查会话）

```text
请只做代码审查，不做实现。重点检查：
1. 是否越界修改
2. 是否存在幂等/审计/落库缺口
3. 是否缺关键测试
4. 是否可能引入回归
5. 是否满足给定 DoD

请先给出 findings，按严重程度排序。
若无 findings，请明确说明残余风险和测试空白。
```

### 6.4 子任务提交格式

建议每个 AI 提交时严格按以下格式返回：

```text
任务名：
commit：
改动摘要：
测试：
- command => pass/fail
风险：
- 风险 1
- 风险 2
```

这样做的好处是：

1. 主控会话能快速比较不同任务状态。
2. 合并时不会遗漏测试和风险说明。
3. 后续回溯时能清楚知道每次改动的上下文。

## 7. 合并策略与证据链

### 7.1 合并顺序

默认合并顺序必须遵循依赖方向：

1. 数据结构与仓储层：
   `migrations`、repo、持久化守卫。
2. 后端业务层：
   API、service、worker、审计、SLA。
3. 契约与门禁层：
   OpenAPI、release gate、脚本。
4. 前端工作台：
   页面、交互、可视化。
5. E2E 与文档层：
   E2E、Runbook、清单、报告。

### 7.2 合并方式

推荐默认使用：

```powershell
git checkout main
git merge --no-ff codex/<task>
```

原因：

1. `--no-ff` 能保留任务边界。
2. 出问题时更容易按任务回滚。
3. 对多 AI 并行开发更友好，证据链更完整。

只有在严格要求线性历史、且任务极小、证据齐全时，才考虑 `--ff-only`。

### 7.3 合并前必须具备的证据

每个分支在进入 `main` 前，至少要有四类证据：

1. 代码证据：
   改动文件范围与任务卡一致。
2. 测试证据：
   指定命令执行通过。
3. 数据证据：
   关键写操作有落库或审计证据。
4. 回滚证据：
   清楚知道要回到哪个提交、需要重跑哪些验证。

### 7.4 合并门禁检查单

```text
[ ] 任务卡存在且边界清晰
[ ] 白名单文件检查通过
[ ] 指定测试全部通过
[ ] 关键写操作具备落库/审计证据
[ ] 风险说明已写明
[ ] 回滚点已确认
[ ] 文档已更新
```

### 7.5 合并后必须执行的动作

1. 立即检查 `git status`，确认未带入额外脏改动。
2. 立即运行至少一条集成级回归命令。
3. 更新评分卡。
4. 如涉及共享文件，通知相关任务重新 rebase 或补回归。

## 8. 发布门禁与验收命令

### 8.1 仓库级标准命令

以下命令是当前仓库的发布基线：

```powershell
pnpm run repo:verify
pnpm run test:backend:release-gate
pnpm --dir apps/erp-web run generate:api
pnpm --dir apps/erp-web build
pnpm run test:e2e:release-gate
```

### 8.2 后端关键验证命令

与售后工业级收敛直接相关的命令建议纳入高频回归：

```powershell
cargo test -p erp-api --test after_sales_state_machine_guard -- --nocapture
cargo test -p erp-api --test after_sales_finance_reconcile -- --nocapture
cargo test -p erp-api --test after_sales_sla_escalation -- --nocapture
cargo test -p erp-common
```

### 8.3 硬阻断规则

满足任一条即 **NO-GO**：

1. `DATABASE_URL` / `TEST_DATABASE_URL` 不可用。
2. 关键测试出现 `skipping ... DATABASE_URL`。
3. 关键测试出现 `pool timed out`。
4. OpenAPI 缺路径、缺权限、缺状态码、缺持久化声明。
5. 写操作没有实际落库/审计证据。
6. 前端表现正常，但后端状态或审计不一致。

## 9. 售后工业级收敛任务包

本节用于把“售后差距”真正拆成可并行、可验收的任务，不再停留在泛泛而谈。

### 9.1 售后任务包总览

| 任务包 | 目标 | 优先级 | 是否可并行 |
| --- | --- | --- | --- |
| A. 状态机与幂等 | 保证售后流转合法、重复请求无重复副作用 | P0 | 可，与 B 串行共享少量文件 |
| B. 财务对账与审计 | 保证退款、补差、台账、审计一致 | P0 | 可，与 A、D 部分协同 |
| C. SLA 与升级 | 保证超时率、升级率口径稳定 | P0 | 可 |
| D. 平台售后联动 | 保证回调、重试、补偿闭环 | P0 | 可，与 B 有交叉 |
| E. 逆向物流与入库 | 保证退货签收、质检、退回入库可追踪 | P1 | 可 |
| F. 换货与补发 | 保证换货单、补发单、出库和原单关联完整 | P1 | 可 |
| G. 客服工作台 | 保证客服视图、异常提示、人工干预可操作 | P1 | 可，在 A-D 稳定后进行 |

### 9.2 任务包 A：状态机与幂等

目标：

1. 明确受理、审核、退款中、退款完成、拒绝、取消、补发中、补发完成等关键状态迁移。
2. 保证重复请求不会造成重复退款、重复补发、重复审计。

完成定义：

1. 每个状态迁移都有明确 guard。
2. 非法状态跳转必须被拒绝。
3. 幂等请求不会造成二次副作用。

必须具备的证据：

1. 状态历史表命中。
2. 操作日志或审计表命中。
3. 至少一条重复请求测试。

建议测试：

```powershell
cargo test -p erp-api --test after_sales_state_machine_guard -- --nocapture
```

### 9.3 任务包 B：财务对账与审计

目标：

1. 退款单、审计日志、财务台账之间保持一致。
2. 局部失败时允许补写审计，但不允许“接口成功却无审计”。

完成定义：

1. 退款动作有落库证据。
2. 审计写入具备补偿机制或幂等补写能力。
3. 金额、币种、单据关联字段可追踪。

建议测试：

```powershell
cargo test -p erp-api --test after_sales_finance_reconcile -- --nocapture
```

### 9.4 任务包 C：SLA 与升级

目标：

1. 超时率、升级率、待处理量等指标口径稳定。
2. 指标不能被查询方式污染。

完成定义：

1. 指标采用明确的快照或累加语义。
2. 默认查询与全量统计口径一致。
3. 告警阈值可配置并可解释。

建议测试：

```powershell
cargo test -p erp-api --test after_sales_sla_escalation -- --nocapture
```

### 9.5 任务包 D：平台售后联动

目标：

1. 外部平台回调、主动拉取、补偿重试形成闭环。
2. 回调失败、重复回调、延迟回调都不会破坏本地真相。

完成定义：

1. 事件去重策略明确。
2. 重试有次数、退避、告警或人工兜底。
3. 失败事件可在工作台中找到并处理。

建议落库证据：

1. outbox / inbox 记录。
2. 操作日志。
3. 审计日志。

### 9.6 任务包 E：逆向物流与入库

目标：

1. 把售后单、退货物流、质检、逆向入库串成同一导航链。
2. 避免“客服能退款，但仓库看不到货”的断层。

完成定义：

1. 退货签收状态与售后状态有关联。
2. 质检结果可回写售后结论。
3. 逆向入库能追踪到原售后单。

### 9.7 任务包 F：换货与补发

目标：

1. 换货单、补发单与原订单、原售后单建立稳定关联。
2. 换货和补发都能进入出库和物流轨迹链路。

完成定义：

1. 原单、售后单、新出库单三者能双向跳转。
2. 重复补发被幂等拦截。
3. 物流状态回写不丢失。

### 9.8 任务包 G：客服工作台

目标：

1. 客服能在一个工作台里看到受理、处理、退款、补发、平台失败事件。
2. 异常原因、SLA 风险和人工操作入口集中呈现。

完成定义：

1. 工单列表、详情、动作栏、异常提示闭环。
2. 人工重试、拒绝、升级、补写审计等动作可用。
3. 权限与角色边界清晰。

### 9.10 当前仓库推荐集成顺序

建议按以下顺序集成，能最大程度降低冲突和返工：

1. Worker-A 状态机与幂等
2. Worker-B 财务对账与审计
3. Worker-C 平台售后联动
4. 主控会话串行集成 `crates/erp-api/src/lib.rs`
5. Worker-E SLA 与客服协同
6. Worker-D 逆向物流 / 补发 / 换货
7. Worker-F 客服工作台与接口编排
8. 最后统一回归 E2E、release gate、Go/No-Go 文档

原因：

1. A、B、C 先守住“数据真相”。
2. `crates/erp-api/src/lib.rs` 在中间串行收口，避免多个 Worker 同时改入口文件。
3. E、D、F 再补表现层和工作台，不会反过来破坏底层一致性。

### 9.11 单人多 AI 的主控会话执行口诀

主控会话每天只做四件事：

1. 拆任务，不代替 Worker 写代码。
2. 锁共享文件，不让并行任务互踩。
3. 收证据，不接受“我觉得应该没问题”。
4. 做集成，不把未验证代码直接并到 `main`。

## 11. Definition of Done（DoD）

### 11.1 任何子任务必须同时满足

1. 功能按任务卡目标完成。
2. 改动范围没有越界。
3. 关键测试通过。
4. 风险被显式说明。
5. 若是写操作，存在落库或审计证据。
6. 若涉及共享文件，已记录并完成邻接任务回归。

### 11.2 工业级 DoD 额外要求

以下任一缺失，都不能算工业级完成：

1. 失败路径未覆盖。
2. 幂等未验证。
3. 审计未落地。
4. 回滚步骤不明确。
5. 文档未同步。

## 12. 冲突处理 SOP

### 12.1 冲突出现时的处理顺序

1. 先暂停两个分支继续扩散改动。
2. 明确业务真相源：
   通常以后端状态机、审计、落库规则为准。
3. 按“真相源优先、表现层后适配”的原则解决。
4. 冲突解决后立即重跑本任务测试。
5. 再重跑相邻任务的关键测试。
6. 在任务记录中写明冲突原因和处理方式。

### 12.2 禁止的冲突处理方式

1. 为了过编译直接删逻辑。
2. 看不懂冲突时整块保留某一侧而不回归。
3. 为了省事跳过数据库测试。
4. 发现落库缺口却先合并、后补修复。

## 13. 日常节奏与周节奏

### 13.1 每日节奏

建议固定四个时间点：

1. `09:30`
   拆任务卡、创建分支/worktree、分配 AI。
2. `11:00`
   第一轮集成窗口，只合并低风险和基础层任务。
3. `15:00`
   中期回归，处理失败测试和共享文件冲突。
4. `18:00`
   第二轮集成窗口，更新评分卡和次日优先级。

### 13.2 每周节奏

建议固定三类活动：

1. 周一：
   明确本周 `P0 / P1 / P2` 任务包。
2. 周中：
   执行一次门禁演练，防止临近发布才发现脚本失效。
3. 周末：
   汇总周评分、返工率、冲突率、回归率，决定是否达到 `4.5+`。

## 14. 常见反模式

以下行为是单人多 AI 开发最常见的失控源：

1. 让多个 AI 直接共享一个长上下文，最后把代码手工拼在一起。
2. 不划白名单，默认允许 AI “顺手优化”。
3. 只看页面效果，不核对后端落库和审计。
4. 发现测试依赖 DB，就直接跳过。
5. 所有任务都堆到一个大分支里，等“差不多了再合并”。
6. 不记录冲突原因，导致同类问题反复发生。
7. 不设每日集成窗口，导致分支长期漂移。
8. 用“以后补文档”替代即时记录，最后没人知道系统为什么这样设计。

## 16. 达到 4.5+ 的最短路径

如果目标是尽快把当前项目推到 `4.5+`，优先级建议如下：

1. 先固化并行机制：
   分支、工作区、任务卡、门禁清单全部标准化。
2. 再守住售后 P0：
   状态机、财务审计、SLA、平台联动必须形成闭环。
3. 再补工作台和逆向执行：
   退货、换货、补发、逆向入库的导航链打通。
4. 最后收口发布治理：
   OpenAPI、release gate、E2E、Go/No-Go 证据统一。

最关键的判断原则是：

**工业级 ERP 的 4.5+，不是页面更多，而是关键链路“正确、稳定、可审计、可回滚”。**
