# Codex 多 AI 并行修改作战手册（目标评分 4.5+）

> 适用场景：一个人同时驱动多个 AI 会话/分支并行开发，并保证可合并、可回滚、可审计。  
> 版本：v2.0  
> 更新日期：2026-04-14

## 1. 目标定义

本手册的目标不是“并行写更多代码”，而是把并行开发做成工业化交付流程，在质量和稳定性上达到 `>= 4.5/5`。

成功标准：

1. 并行开发不互踩：任务边界清楚，冲突可控。
2. 合并可验证：每次合并有完整证据链（测试、审查、回滚点）。
3. 业务链路不退化：售后、退换货、补发货、平台联动关键场景无 P0/P1 回归。
4. 过程可复制：换人或新增 AI 会话后，流程仍稳定运行。

## 2. 4.5+ 评分模型（统一口径）

总分 5.0，按 6 维加权计算：

| 维度 | 权重 | 评分口径（4.5+） |
| --- | --- | --- |
| 并行隔离 | 15% | 100% 改动在任务分支，0 次在 `main` 直接开发 |
| 代码与测试 | 25% | P0/P1 变更必须有自动化测试，关键链路通过率 `>= 98%` |
| 合并治理 | 20% | 100% 合并经过门禁，冲突与决策可追溯 |
| 可观测与审计 | 15% | 核心链路具备指标、日志、审计三件套 |
| 交付效率 | 15% | 平均 lead time 稳定下降，返工率持续下降 |
| 稳定性 | 10% | 近两周无 P0 回归，P1 在 SLO 窗口内闭环 |

评分公式：

```text
总分 = Σ(维度得分 × 权重)
```

推荐阈值：

1. `>= 4.5`：工业级并行交付可持续。
2. `4.0 ~ 4.49`：可规模化试运行，但需持续补短板。
3. `< 4.0`：不建议继续扩并行，先补治理能力。

## 3. Codex 并行任务模型（单人多 AI）

### 3.1 角色分工

1. 主会话（Integrator）：负责任务拆分、门禁检查、最终合并。
2. 子会话（Worker A/B/C）：按白名单文件实施开发，不越界修改。
3. 审查会话（Reviewer，可选）：专门做回归风险和测试充分性检查。

### 3.2 任务卡模板（每个 AI 一张）

每张任务卡必须包含：

1. `目标`：一句话定义可验收结果。
2. `边界`：允许修改文件白名单。
3. `禁区`：禁止修改模块清单。
4. `测试`：必须执行的最小测试命令。
5. `交付`：提交哈希 + 测试证据 + 风险说明。

任务卡示例：

```text
任务名：aftersales-sla-gauge
目标：修复售后 SLA 分母统计污染，改为快照语义
边界：
- crates/erp-common/src/telemetry.rs
- crates/erp-api/src/aftersales/service.rs
禁区：
- apps/erp-web/src/pages/orders/**
测试：
- cargo test -p erp-common
- cargo test -p erp-api --test after_sales_sla_escalation -- --nocapture
交付：
- commit hash
- 通过命令列表
- 残余风险（如：全量回归待 nightly）
```

## 4. 分支与工作区策略（防互踩核心）

### 4.1 一任务一分支一工作区

命名规范：

1. 分支：`codex/<domain>-<scope>-<yyyymmdd>`
2. 工作区：`../erp-<domain>-<scope>`

示例：

```powershell
git checkout -b codex/aftersales-sla-20260414
git worktree add ../erp-aftersales-sla codex/aftersales-sla-20260414
```

强制规则：

1. 禁止两个 AI 写同一分支。
2. 禁止直接在 `main` 开发。
3. 禁止跨任务顺手改动（非白名单文件视为越界）。

### 4.2 共享文件治理

针对高冲突文件（如 `lib.rs`、`openapi/*.yaml`）：

1. 采用“时段锁”：同一时间只允许一个任务修改。
2. 采用“串行集成”：先合并基础层，再合并业务层，再前端层。
3. 冲突后必须补跑受影响测试，禁止“只过编译就合并”。

## 5. 合并门禁（Merge Gate）

任何任务分支合并到 `main` 前，必须全部满足：

1. 变更范围符合任务卡边界（无越界文件）。
2. 指定测试全部通过，且输出可追溯。
3. 无已知 P0/P1 未处理缺陷。
4. 回滚路径明确（可回滚到前一稳定提交）。
5. 文档同步（计划、变更记录、风险说明至少一项）。

门禁检查单（建议每次复制使用）：

```text
[ ] 边界检查通过
[ ] 单元/集成测试通过
[ ] 回归风险评估通过
[ ] 回滚点已确认
[ ] 文档已更新
```

## 6. 工业级售后链路的并行开发重点

围绕“退货退款 / 换货 / 补发货 / 平台售后联动”，并行任务建议如下：

1. 任务 A（状态机与幂等）：保障状态流转合法、重复请求无重复副作用。
2. 任务 B（财务对账与审计）：保证退款单、台账、审计日志一致。
3. 任务 C（SLA 与升级）：保证超时率、升级率指标口径稳定。
4. 任务 D（平台联动）：保证外部平台回调、重试、补偿闭环。
5. 任务 E（前端操作台）：保证客服视图、异常提示、人工干预可用。

合并顺序建议：A/B -> C -> D -> E（先守住数据正确性，再做表现层）。

## 7. 冲突与故障处理 SOP

### 7.1 冲突处理

1. 先判断“谁是业务真相源”（通常以后端状态机/审计为准）。
2. 再合并表现层改动（UI/文案/查询逻辑）。
3. 冲突解决后重跑：本任务测试 + 受影响邻接任务测试。

### 7.2 红线（触发即暂停合并）

1. 出现“接口成功但无落库/无审计”。
2. 幂等失效导致重复副作用（重复退款、重复出库、重复补发）。
3. 指标被查询行为污染，导致报表不可解释。
4. 无法给出清晰回滚步骤。

## 8. 4 周冲刺到 4.5+ 的执行节奏

第 1 周（并行机制稳定化）：

1. 全任务分支化 + worktree 化。
2. 统一任务卡模板与门禁清单。
3. 固定每日 2 次集成窗口（例如 11:00 / 18:00）。

第 2 周（质量基线抬升）：

1. 为售后关键链路补齐幂等、补偿、失败路径测试。
2. 对高风险变更强制双人/双 AI 复核。

第 3 周（观测与审计闭环）：

1. 指标、日志、审计三件套完整落地。
2. 告警阈值和处置手册可执行。

第 4 周（演练与复核）：

1. 按 Go/No-Go 清单执行一次完整演练。
2. 按第 2 节评分模型复盘并输出改进计划。

## 9. 每日执行节拍（单人可落地）

1. 09:30 前：拆分任务卡并分配给各 AI 会话。
2. 11:00：第一轮集成窗口，合并低风险任务。
3. 15:00：中期回归，处理冲突和失败测试。
4. 18:00：第二轮集成窗口，输出当日评分与次日优先级。

## 10. 最小命令集

```powershell
# 1) 创建任务分支
git checkout -b codex/<task>

# 2) 创建独立工作区
git worktree add ../erp-<task> codex/<task>

# 3) 查看本任务改动范围
git status --short
git diff --name-only

# 4) 合并任务到 main
git checkout main
git merge --no-ff codex/<task>

# 5) 推送
git push origin main
```
