# 一体化数据作业台工业级改造设计

**日期：** 2026-04-19

## 1. 文档目标

本设计用于替换当前 ERP Web 中以“Workbench / 工作台”作为实现导向的页面体系，建立一套面向企业级电商 ERP 的统一模板标准。

新的正式中文名称定义为：

- **一体化数据作业台**

该名称代表一类标准化页面，不代表某个具体业务页面。订单审核、订单复核、订单查询、商品、渠道、库存等所有“以主数据表为中心”的页面，都应最终纳入这一家族。

代码层在迁移期间允许保留历史导出名以减少改造成本，例如：

- `WorkbenchPageTemplate`
- `WorkbenchToolbar`

但从产品语言、文档规范、设计评审和后续扩展层面，统一采用中文名称：

- **一体化数据作业台**

## 2. 工业级目标

本次改造的唯一目标不是“把页面做得更像”，而是建立一套可复制、可治理、可规模化扩展的统一内核。

工业级标准需要同时满足以下要求：

1. 新建一个主数据作业台页面时，开发者不再自行设计主表交互、左右区域联动、子表切换、列筛选和状态恢复。
2. 页面之间的差异只体现在数据范围、业务动作、字段定义和业务语义上，而不是基础交互和视觉行为上。
3. 用户在审核、复核、查询、商品、渠道、库存等页面之间切换时，不需要重新学习交互逻辑。
4. 统一能力必须具备集中治理能力，包括列配置、保存视图、分页恢复、筛选联动、详情联动、子表联动、导出、打印、帮助与快捷操作。
5. 页面实现必须从“复制旧页面结构”升级为“按统一契约声明式接入”。

## 3. 适用范围

本设计适用于所有满足以下特征的 ERP Web 页面：

1. 页面核心是中央主数据表。
2. 页面具备顶部工具栏。
3. 页面具备左侧过滤区。
4. 页面可选具备右侧详情区。
5. 页面可选具备底部子表区。

标准结构定义为：

1. 顶部工具栏
2. 左侧过滤
3. 中央主表
4. 右侧详情
5. 底部子表

其中右侧详情和底部子表允许按页面场景隐藏，但隐藏不代表脱离统一内核，而是统一内核的能力裁剪。

## 4. 非目标

以下内容不属于本设计的首要目标：

1. 一次性重写所有历史页面。
2. 一次性统一所有后端接口协议。
3. 重做整个 ERP 的视觉主题系统。
4. 为每个业务领域建立独立模板。
5. 保留现有 `review / recheck / query` 三分叉主表路线作为长期标准。

## 5. 当前问题诊断

当前仓库已经完成了一部分工作台骨架统一，但尚未达到工业级标准，主要问题如下：

1. 页面壳体已有统一入口，但主表内核仍然分叉。
2. 页面仍自行管理一部分选择、筛选、详情联动和子表加载逻辑。
3. 不同页面的主表实现存在不同能力边界，导致新页面接入时仍要重新选择技术路线。
4. 现有 `OrderReviewMainGrid`、`OrderExceptionsMainGrid`、`ErpDataGridNext` 更接近“历史实现”，而非统一工作台内核。
5. 当前 `OrderWorkbenchMainGridEntry` 的分发方式只能解决页面入口统一，不能解决交互内核统一。

结论是：

- 当前体系是“统一页面壳 + 分叉主表实现”
- 工业级目标需要升级为“统一页面壳 + 统一数据作业台内核 + 页面配置式接入”

## 6. 核心产品决策

### 6.1 顶层页面家族不变，但数据工作台标准重构

ERP Web 仍保留两类长期页面家族：

1. 一体化数据作业台
2. 设置型页面

本次改造聚焦第一类。

### 6.2 采用强约束单内核

所有主数据作业台页面必须接入同一套工作台内核，统一以下能力：

1. 主表实现
2. 行选择与多选逻辑
3. 焦点记录逻辑
4. 列筛选与列配置
5. 右侧详情联动
6. 底部子表联动
7. 工具栏搜索、导出、打印、帮助
8. 保存视图、分页恢复、工作台状态恢复

页面层不得再自行选择另一套主表实现路线。

### 6.3 页面只允许声明业务差异

具体业务页面只负责声明：

1. 数据范围
2. 左侧过滤维度
3. 主表列定义
4. 业务动作
5. 右侧详情字段
6. 底部子表定义

页面不得重新定义基础交互、区域行为和统一视觉规则。

## 7. 新标准命名体系

### 7.1 正式中文名称

统一名称：

- **一体化数据作业台**

### 7.2 迁移期代码兼容命名

迁移期间允许保留以下导出名作为兼容层：

1. `WorkbenchPageTemplate`
2. `WorkbenchToolbar`

但内部应逐步替换为新的语义层：

1. `DataWorkbenchKernel`
2. `DataWorkbenchMainGrid`
3. `DataWorkbenchRightPanel`
4. `DataWorkbenchBottomTabs`
5. `DataWorkbenchPageConfig`

### 7.3 旧术语退役

以下旧术语保留为历史兼容，不再作为长期规范入口：

1. `WorkbenchMainTableTemplate`
2. `WorkbenchToolbarTemplate`
3. `OrderWorkbenchMainGridEntry` 的三分叉主表路线
4. 页面自己拼接主表交互逻辑的实现方式

## 8. 目标架构

新的工业级架构分为三层：

### 8.1 骨架层

骨架层负责统一页面布局，不承载业务语义。

职责包括：

1. 顶部工具栏区域挂载
2. 左侧过滤区域挂载
3. 中央主表容器挂载
4. 右侧详情容器挂载
5. 底部子表容器挂载
6. 页脚、分页与浮层插槽挂载
7. 字号、节奏、基础视觉骨架

这一层应继续由现有 `WorkbenchPageTemplate` 演进承担，但其职责必须严格限制在布局层。

### 8.2 内核层

内核层是本次改造的核心，也是工业级标准的真正主体。

建议建立统一内核概念：

- `DataWorkbenchKernel`

其职责包括：

1. 主表控制器
2. 选择控制器
3. 焦点记录控制器
4. 列筛选控制器
5. 列配置持久化
6. 保存视图
7. 右侧详情联动
8. 底部子表联动
9. 加载态、空态、错误态
10. 工具栏标准动作
11. 统一快捷操作与帮助入口

### 8.3 页面配置层

页面配置层负责把具体业务接入统一内核。

页面只需提供：

1. 数据适配器
2. 左侧过滤 schema
3. 主表列 schema
4. 工具栏动作 schema
5. 右侧详情 schema
6. 底部子表 schema

## 9. 统一契约设计

### 9.1 数据适配器契约

建议建立：

- `DataWorkbenchDataAdapter`

职责：

1. 获取主表数据
2. 获取右侧详情数据
3. 获取底部子表数据
4. 定义主键
5. 定义记录唯一标识
6. 处理刷新与重试

页面不直接把接口细节暴露给主表实现，而是通过适配器接入。

### 9.2 左侧过滤契约

建议建立：

- `DataWorkbenchFilterSchema`

职责：

1. 定义左侧分组
2. 定义节点层级
3. 定义统计项
4. 定义节点点击如何映射查询条件
5. 定义筛选口径说明

### 9.3 主表列契约

建议建立：

- `DataWorkbenchColumnSchema`

职责：

1. 定义列
2. 定义列类型
3. 定义可排序性
4. 定义可筛选性
5. 定义渲染器
6. 定义列配置持久化能力

### 9.4 工具栏契约

建议建立：

- `DataWorkbenchToolbarSchema`

职责：

1. 统一搜索入口
2. 统一导出入口
3. 统一打印入口
4. 统一帮助入口
5. 页面级业务动作插槽
6. 页面级辅助动作插槽

### 9.5 右侧详情契约

建议建立：

- `DataWorkbenchDetailSchema`

职责：

1. 记号区
2. 主字段区
3. 轻量工具区
4. 可编辑字段区
5. 空态与加载态说明

### 9.6 底部子表契约

建议建立：

- `DataWorkbenchBottomTabSchema`

职责：

1. 定义子表 tab
2. 定义 tab 加载方式
3. 定义 tab 与主表焦点联动方式
4. 定义无焦点时的空态

## 10. 统一交互规则

### 10.1 工具栏

所有一体化数据作业台页面必须具备统一工具栏行为：

1. 搜索输入位置一致
2. 导出位置一致
3. 打印位置一致
4. 帮助位置一致
5. 页面业务动作只能插入统一动作区

### 10.2 主表

所有一体化数据作业台页面必须具备统一主表行为：

1. 统一选择列样式
2. 统一单选 / 多选规则
3. 统一焦点记录规则
4. 统一双击行为
5. 统一上下文菜单入口
6. 统一列筛选入口
7. 统一列配置入口
8. 统一滚动与选中视觉反馈

### 10.3 右侧详情

所有一体化数据作业台页面必须具备统一详情联动规则：

1. 主表焦点变化后统一刷新详情
2. 无焦点记录时统一空态
3. 加载中统一反馈
4. 详情刷新失败统一反馈

### 10.4 底部子表

所有一体化数据作业台页面必须具备统一底部联动规则：

1. 主表焦点变化后统一刷新子表
2. 每个子表 tab 的加载态一致
3. 无焦点记录时统一空态
4. tab 样式与切换位置一致

### 10.5 状态恢复

统一保存以下状态：

1. 搜索值
2. 左侧过滤状态
3. 主表列筛选
4. 选中记录
5. 焦点记录
6. 分页
7. 右侧 / 底部显隐状态

## 11. 页面接入方式

未来新增页面时，目标流程应简化为：

1. 选择数据范围
2. 定义左侧过滤 schema
3. 定义主表列 schema
4. 定义业务动作 schema
5. 定义右侧详情 schema
6. 定义底部子表 schema
7. 注册页面并完成测试

开发者不应再手写：

1. 选择逻辑
2. 焦点逻辑
3. 列筛选控制器
4. 详情联动控制器
5. 子表联动控制器
6. 导出 / 打印 / 帮助的统一动作位置

## 12. 迁移策略

### 阶段一：冻结旧路线

立即冻结以下行为：

1. 不再新增新的工作台主表实现
2. 不再新增新的页面级主表模板
3. 不再扩大 `review / recheck / query` 三分叉路线

### 阶段二：抽取统一内核

从现有实现中抽取共性能力：

1. 从 `OrderReviewMainGrid` 抽主表共性行为
2. 从当前工作台控制器中抽选择与焦点逻辑
3. 从当前工具栏中抽搜索 / 导出 / 打印 / 帮助统一动作
4. 从当前详情区和底部子表中抽统一空态、加载态和联动规则

### 阶段三：订单域样板改造

以订单域作为首批样板：

1. 订单审核
2. 订单复核
3. 订单查询

三页全部改为同一内核接入，仅在数据范围、过滤 schema、列 schema 与业务动作上保留差异。

### 阶段四：推广到全站主数据作业台页面

订单域稳定后，再推广到：

1. 商品
2. 渠道
3. 库存
4. 其他主数据作业台页面

### 阶段五：退役旧实现

在迁移完成后，逐步退役：

1. 旧的分叉主表入口
2. 页面手写的选择 / 联动逻辑
3. 历史模板壳名词与旧规范描述

## 14. 风险与控制

主要风险：

1. 直接把旧业务页硬套到某一现有主表，导致语义不匹配。
2. 先改页面、后补内核，导致改造过程反复返工。
3. 以“看起来像”为目标，忽略交互契约统一。

控制原则：

1. 先抽统一内核，再迁页面。
2. 先在订单域做样板，再推广。
3. 样式、交互、状态恢复、联动必须一起统一，而不是只统一外观。

## 15. 验收标准

当以下条件全部满足时，视为完成一体化数据作业台标准落地：

1. 新页面不再选择不同主表实现路线。
2. 新页面只通过数据适配器与 schema 接入。
3. 用户在不同主数据作业台页面中的基础操作一致。
4. 列筛选、状态恢复、详情联动、子表联动全部由统一内核承担。
5. 旧的分叉主表路线被明确标记为过渡兼容，而非长期标准。

## 16. 最终结论

工业级标准电商 ERP 模板，不应建立在“多个页面共享一个外壳”之上，而应建立在：

1. 统一骨架
2. 统一内核
3. 页面配置式接入

本次改造的正式方向是：

- 以 **一体化数据作业台** 取代现有分叉工作台思路
- 保留骨架层
- 重建统一内核层
- 将页面层收敛为配置和业务编排层

这将成为 ERP Web 后续所有主数据作业台页面的唯一长期演进方向。
