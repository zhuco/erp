# 项目规范化与 ErpDataGrid 重构设计

- 日期：2026-03-24
- 状态：设计已确认，待进入实施计划
- 适用范围：`F:\erp`
- 约束前提：
  - `ErpDataGrid` 目标对标 AG Grid 企业版体验
  - 不引入任何付费 grid
  - 必须纯开源、可商用
  - 第一批真实验收页面为“订单审核页”和“订单列表页”

## 1. 背景

当前仓库已经具备一定的工程门禁、前端验收脚本、业务规范文档和 `ErpDataGrid` 基础设施，但这些能力存在三个结构性问题：

1. 工程规范分散在 README、脚本、CI 和多份运维文档中，缺少统一的根级基线配置。
2. 代码边界已经出现明显失控信号，前后端都存在超大文件和跨层耦合。
3. `ErpDataGrid` 已经从“组件”演变成“平台层”，但底层仍然深度绑定 `Tabulator`，导致选择、多选、钩选、自由框选、滚动保持和业务动作之间频繁冲突。

本设计的目标不是做一次零散修补，而是建立一条能够长期收敛项目质量的主线，同时把 `ErpDataGrid` 从定制集成件升级为真正可维护的开源企业级表格平台层。

## 2. 目标

### 2.1 项目规范化目标

1. 将仓库的工程门禁从“命令约定”升级为“仓库固化规则”。
2. 将前端、后端、CI、文档和脚本的规范入口统一。
3. 为后续功能开发建立可执行、可复查、可验收的协作流程。

### 2.2 ErpDataGrid 目标

1. 在纯开源可商用约束下，实现接近 AG Grid 企业版的核心使用体验。
2. 重建稳定的选择模型、范围模型、列状态模型和批量动作模型。
3. 保留业务页面感知到的 `ErpDataGrid` 产品层 API，降低业务接入面重写成本。
4. 以“订单列表页”和“订单审核页”作为第一批真实验收场景。

## 3. 非目标

本次设计不包含以下内容：

1. 不追求第一阶段补齐所有高级能力，例如图表、树表、主从明细、透视分析的全量重建。
2. 不将整个仓库一次性重构为全新架构。
3. 不在旧 `Tabulator` 内核上继续叠加长期能力扩展。
4. 不把自由框选直接定义为业务批量动作的目标集合。

## 4. 当前问题概览

### 4.1 工程基线问题

当前仓库缺少若干根级规范文件，导致格式、忽略规则、静态检查策略和临时产物管理没有统一落点。现状主要依赖 README、脚本和人工记忆维持。

### 4.2 CI 与门禁漂移

前端存在两套 workflow，版本和步骤不完全一致，容易出现本地、CI、验收脚本三套口径不一致的问题。

### 4.3 代码边界问题

仓库中已出现多个超大文件与重耦合单元，说明“按功能堆积”已经超过可维护阈值。此类文件将显著放大后续改动风险。

### 4.4 ErpDataGrid 架构问题

当前 `ErpDataGrid` 的主要问题不是单一功能缺失，而是底层交互模型已经被大量手工补丁和引擎特定逻辑拉到极限：

1. 类型层直接依赖 `Tabulator` 定义，导致产品层无法与底层引擎解耦。
2. 多个 hook 与工具函数直接查找、操作或 patch `Tabulator` 实例与 prototype。
3. 表格选择、范围、滚动、右键菜单、排序和刷新之间缺少统一状态核心。
4. 业务页无法只依赖稳定语义，还需要承受底层实现细节的影响。

## 5. 方案比较

### 5.1 方案一：继续以 Tabulator 为底座收敛

做法：

- 保留现有底座
- 继续拆分 `ErpDataGridImpl`
- 逐项修补选择、范围和滚动问题

优点：

- 短期业务接入成本最低
- 第一眼看起来最省改造量

缺点：

- 无法从根上解决状态模型混乱的问题
- 后续每补一项企业级体验，都会增加技术债
- 继续放大对 `Tabulator` 行为细节的依赖

结论：

- 不推荐作为长期路线

### 5.2 方案二：保留产品层 API，重建引擎适配层

做法：

- 保留 `ErpDataGrid` 对业务页暴露的核心概念
- 新建独立的表格状态核心
- 使用开源 headless 方案重建渲染与交互
- 底层采用 `TanStack Table + TanStack Virtual + dnd-kit + React 事件层`

优点：

- 最符合纯开源可商用约束
- 企业版体验的关键能力掌握在自有状态模型中
- 便于对真实业务页逐步切换
- 最适合作为 ERP 工作台型复杂表格基座

缺点：

- 前期需要投入抽象层建设成本
- 不能期待“一周内靠补丁彻底完成”

结论：

- 推荐采用

### 5.3 方案三：改用开源 canvas/grid 内核

做法：

- 保留产品层 API
- 底层迁移到偏 spreadsheet 或 canvas 风格的开源 grid

优点：

- 范围选择和高密度表格性能可能更强

缺点：

- 对复杂 React 单元格和 ERP 业务交互的适配成本更高
- 订单审核类工作台页面并非纯二维数据表，收益不如方案二稳定

结论：

- 可作为备选，不作为首选路线

## 6. 推荐方案

采用方案二：

> 保留 `ErpDataGrid` 产品层，重建状态核心和引擎适配层，逐步从 `Tabulator` 迁移到纯开源 headless 组合。

该方案的核心价值在于：

1. 保留当前业务接入的主要语义，避免所有页面重写。
2. 把“选择、框选、复制、列状态、批量编辑”的核心体验从第三方引擎行为中抽离出来。
3. 允许后续继续扩展企业级能力，而不是被单一引擎的限制牵着走。

## 7. 项目规范化设计：A -> B -> C

## 7.1 A：工程门禁统一

目标：把规范固化为仓库规则，而不是人肉约定。

交付项：

1. 根级基线文件统一：
   - `.editorconfig`
   - `.gitignore`
   - `rustfmt.toml`
   - `clippy.toml`
   - Node / pnpm / Rust 版本基线说明
2. 根级命令统一：
   - `lint`
   - `typecheck`
   - `test`
   - `build`
   - `accept:web`
   - `accept:backend`
   - `accept:all`
3. CI 收敛：
   - 前端只保留一套标准 workflow
   - README、脚本和 CI 统一引用同一套命令入口
4. 生成产物与临时文件治理：
   - 明确忽略 `node_modules`、`target`、日志、临时调试文件、`.superpowers/`

验收标准：

1. 本地、脚本、CI 三套入口执行的是同一套命令。
2. 新成员只看一份工程规范文档即可完成环境准备和门禁执行。
3. 同一项门禁不再出现多份互相漂移的实现。

## 7.2 B：代码结构治理

目标：让边界清晰、单元可维护，而不是单纯追求“把代码拆碎”。

交付项：

1. 为前后端分别建立模块职责约束和超大文件拆分规则。
2. 优先治理超大文件和跨层耦合点：
   - `crates/erp-api/src/lib.rs`
   - `apps/erp-web/src/pages/orders/OrderReviewPage.tsx`
   - `apps/erp-web/src/pages/orders/OrdersPage.tsx`
   - `apps/erp-web/src/components/erp-data-grid/ErpDataGridImpl.tsx`
3. 对基础设施类模块建立三层边界：
   - 产品层
   - 状态/能力层
   - 引擎/实现层

验收标准：

1. 业务页不再直接依赖底层 grid 引擎细节。
2. 大文件拆分后，模块职责能用一句话说清楚。
3. 新增需求优先落在已有边界内，不再继续堆积到单个巨型文件。

## 7.3 C：文档与协作流程

目标：把“会做”升级成“团队可重复执行”。

交付项：

1. 文档分层：
   - 工程规范
   - 架构决策记录
   - 模块 / 页面设计文档
   - 验收清单
2. 基础设施或跨页面改造必须先产出设计文档，再进入实施计划。
3. 关键基础设施必须具备“双验收机制”：
   - 调试页能力验收
   - 真实业务页验收

验收标准：

1. 后续类似 `ErpDataGrid` 的大改动都有可回溯 spec。
2. 文档入口收敛，不再让规范散落在报告与临时文档中。

## 8. ErpDataGrid 专项设计

## 8.1 产品定位

`ErpDataGrid` 不再视为“对第三方表格的薄封装”，而是 ERP 前端的表格平台层。其职责包括：

1. 定义对业务页面稳定暴露的列、选择、筛选、状态栏、批量动作、上下文菜单等语义。
2. 对接不同类型的业务表格页面，而不是只服务单一场景。
3. 保证关键交互在所有接入页上的一致性。

## 8.2 目标架构

建议采用以下分层：

### 第一层：产品层

职责：

- 向业务页暴露稳定 API
- 管理筛选栏、状态栏、导出入口、批量编辑入口、上下文菜单等产品能力

原则：

- 不直接依赖底层 grid 实例类型

### 第二层：状态核心

职责：

- 管理引擎无关的核心状态：
  - 行选择状态
  - 活动单元格状态
  - 范围选择状态
  - 列状态
  - 排序状态
  - 过滤状态
  - 剪贴板状态
  - 批量编辑目标状态

原则：

- 所有复杂交互冲突在这一层统一裁决

### 第三层：引擎适配层

职责：

- 将状态核心映射为具体渲染与事件行为
- 当前推荐实现为：
  - `TanStack Table`
  - `TanStack Virtual`
  - `dnd-kit`
  - React DOM 事件层

原则：

- 适配器可以替换，状态语义不变

### 第四层：页面接入层

职责：

- 将 `订单列表页`、`订单审核页` 等业务页面接入统一能力
- 页面只组合产品层能力，不再处理底层选择细节

## 8.3 核心状态模型

必须显式拆分以下状态：

### 行选择状态

- 负责复选框、全选、反选、Shift 连选、Ctrl/Cmd 增量选择
- 输出给批量业务动作使用

### 活动单元格状态

- 负责键盘导航、焦点可见性、复制锚点

### 范围选择状态

- 负责自由框选、鼠标拖拽范围、键盘扩展、跨滚动保持、复制范围

### 列状态

- 负责列顺序、列宽、固定、显隐、持久化

### 排序与过滤状态

- 负责本地与远程模式切换、多列排序、状态栏统计一致性

### 批量编辑目标状态

- 只认行选择状态
- 不直接认范围选择状态

## 8.4 关键交互原则

为避免企业场景中的误操作，必须明确以下原则：

1. 范围选择主要用于查看、复制、未来单元格编辑，不直接等于业务批量动作目标。
2. 业务批量动作只基于显式行选择集合。
3. 右键菜单必须明确作用于当前行或当前选中集合，规则不可摇摆。
4. 排序、过滤、刷新和滚动不应破坏用户已形成的选择意图。

## 8.5 迁移节奏

本次改造分五个阶段执行：

### 阶段 0：冻结旧内核扩展

要求：

- 旧 `Tabulator` 内核不再新增长期功能
- 仅处理阻断性 bug

### 阶段 1：建立新内核调试页

目标：

- 不接真实页面，先验证核心交互

必须完成的能力：

1. 单选与多选
2. Shift 连选
3. Ctrl/Cmd 增量选择
4. 复选框列
5. 表头全选
6. 自由框选
7. 滚动中的范围保持
8. 区域复制
9. 列拖拽
10. 列冻结
11. 列宽调整
12. 列状态持久化

### 阶段 2：接入订单列表页

原因：

- `订单列表页` 更接近标准高密度业务表格，适合作为第一批真实落地页

### 阶段 3：接入订单审核页

原因：

- `订单审核页` 的上下文菜单、详情联动和业务动作更复杂，适合在核心能力稳定后接入

### 阶段 4：清理旧引擎依赖

目标：

- 移除旧 `Tabulator` 直接依赖
- 清理 prototype patch 和实例查找逻辑

## 8.6 第一阶段验收标准

### 订单列表页

必须满足：

1. 鼠标点选、复选框点选、Shift 连选、Ctrl/Cmd 增量选择行为一致。
2. 排序、过滤、列调整后，用户的行选择和列状态不丢失。
3. 快速滚动后仍能稳定显示活动行或活动单元格。
4. 复制范围的内容与当前可视列顺序一致。
5. 表头全选规则清晰且固定，默认作用于当前可见数据集或当前筛选结果。

### 订单审核页

必须满足：

1. 右键菜单始终作用于用户预期的目标行集合。
2. 行选择、活动行、详情联动规则固定，不因刷新或滚动跳变。
3. 框选不会误触发业务批量动作。
4. 批量审核、批量修改、批量导出能够明确显示目标行数。
5. 数据刷新后，如记录仍存在，则尽可能恢复选择状态；如记录已消失，则稳定移除。

## 8.7 测试策略

测试分三层：

### 调试页能力测试

覆盖：

1. 选择
2. 范围
3. 复制
4. 列状态
5. 焦点
6. 滚动保持

### 页面级 E2E

至少覆盖：

1. 订单列表页
2. 订单审核页

### 状态模型单测

重点覆盖：

1. Shift 连选范围计算
2. 范围状态与行选择状态分离
3. 排序 / 过滤后的选择保持
4. 刷新后的状态恢复
5. 列状态持久化

## 8.8 风险与控制措施

### 风险一：一边换引擎，一边继续扩旧内核

控制：

- 明确冻结旧内核新增功能

### 风险二：业务页继续依赖底层实例

控制：

- 先抽离引擎无关类型，再接页面

### 风险三：把范围选择直接等同于业务动作

控制：

- 强制区分范围选择与行选择

### 风险四：先接入最复杂页面，导致问题难定位

控制：

- 先 `订单列表页`，再 `订单审核页`

### 风险五：第一阶段贪多求全

控制：

- 优先稳定核心交互，不把所有高级分析能力一次性拉齐

## 9. 实施顺序建议

建议按两条主线推进：

### 主线一：项目规范化

顺序：

1. 收敛根级配置与忽略规则
2. 收敛脚本与 CI 入口
3. 补统一工程规范文档
4. 建立结构治理规则

### 主线二：ErpDataGrid 重构

顺序：

1. 抽离引擎无关类型
2. 建状态核心
3. 建调试页新内核
4. 接入订单列表页
5. 接入订单审核页
6. 清理旧引擎依赖

两条主线的关系：

- 主线一先落基础规范，减少后续重构过程中的漂移
- 主线二在规范框架内执行，避免再造一个新的“特殊区域”

## 10. 已确认决策

以下决策已在本次设计讨论中确认：

1. 项目规范化按 `A -> B -> C` 顺序推进。
2. `ErpDataGrid` 不继续走“Tabulator 上追加补丁”的长期路线。
3. 底层 grid 引擎允许替换。
4. 不引入任何付费 grid。
5. 目标对标 AG Grid 企业版体验。
6. 第一批真实验收页面为“订单审核页”和“订单列表页”。
