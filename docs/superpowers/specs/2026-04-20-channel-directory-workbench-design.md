# 渠道目录一体化工作台重构设计
**日期**: 2026-04-20

## 1. 文档目标

本设计用于将当前挂载在 `/channels` 的页面，重构为符合企业级电商 ERP 标准的 **渠道目录** 二级目录页。

本次重构采用已确认的方案 A：

1. 保留一级菜单 `目录`
2. 将现有目录入口改为二级菜单 `渠道目录`
3. 将 `/channels` 页面从“店铺接入工作台”纠正为“销售渠道主数据工作台”
4. 页面统一接入 **一体化数据作业台**
5. 页面布局固定为：
左侧筛选 + 中央主表 + 右侧详情
6. 不启用底部子表
7. 不启用记号能力

本次设计同时固定一个额外约束：

- **渠道目录的 UI 页面存放方式必须与其它二级目录页保持同级规范**

也就是页面入口、样式、模型和面板文件都应收敛在 `src/pages/channels` 域内，不再继续沿用“订单工作台语义组件 + 店铺接入逻辑混合”的旧结构。

## 2. 现状诊断

当前 [ChannelsPage.tsx](/F:/erp/apps/erp-web/src/pages/channels/ChannelsPage.tsx) 虽然挂在渠道位置，但实际主数据接入的是 `shops`，页面行为也围绕店铺授权、Token 刷新、店铺接入展开。

这带来四个问题：

1. 页面名称是“渠道目录”，实际主数据却是店铺，语义错误
2. 页面虽然使用了工作台外壳，但主表、左侧筛选和右侧详情仍然借用了订单审核语义
3. 页面域模型与真实业务边界不一致，导致后续新增“渠道目录 / 店铺目录 / 渠道服务购买页”时会持续纠缠
4. 现有页面文件组织不符合二级目录页的标准做法，不利于后续统一维护

结论：

- `/channels` 必须被扶正为“渠道目录”
- 现有店铺接入语义不得继续保留在渠道目录主页面中
- 页面要在统一工作台壳之上，重新定义渠道域自己的数据、筛选、列和详情

## 3. 业务定义

### 3.1 页面职责

渠道目录用于维护 ERP 内部的 **销售渠道主数据**，覆盖线上渠道与线下渠道。

页面负责：

1. 渠道列表查询与筛选
2. 渠道新建、修改、删除、停用
3. 渠道主数据字段维护
4. 渠道服务入口导航
5. 渠道授权入口导航

页面不负责：

1. 店铺授权回调处理
2. 店铺 Token 状态维护
3. 店铺接入列表管理
4. 店铺同步任务明细
5. 底部子表式业务明细联动

### 3.2 主数据范围

渠道目录主数据定义为“销售渠道”，包括：

1. 线上渠道
2. 线下渠道

这里的“渠道”不是店铺，不是平台接口，不是店铺授权实例，而是 ERP 内部可被订单、售后、履约和渠道服务使用的业务主数据对象。

## 4. 目标页面结构

渠道目录必须接入一体化数据作业台，页面结构固定如下：

1. 顶部工具栏
2. 左侧筛选面板
3. 中央主表
4. 右侧详情面板

明确关闭以下区域：

1. 底部子表
2. 右侧记号区

对应的一体化数据作业台接入原则：

1. `leftPanelVisible = true`
2. `rightPanelVisible = true`
3. `bottomPanelVisible = false`
4. 不传入记号相关 schema 或交互配置

## 5. 渠道主数据模型

现有 [channels.ts](/F:/erp/apps/erp-web/src/api/channels.ts) 只包含平台、名称、部门、负责人、抽佣公式、默认仓、手工建单、手工售后、状态等基础字段，无法满足本次业务要求。

本次需要将渠道模型扩展为真正的渠道主数据。

### 5.1 必须字段

建议主数据字段如下：

1. `channel_id`
2. `name`
3. `channel_type`
4. `platform`
5. `contact_name`
6. `contact_phone`
7. `contact_address`
8. `department`
9. `owner`
10. `commission_formula`
11. `default_warehouse_id`
12. `allow_manual_order`
13. `allow_manual_after_sales`
14. `status`
15. `created_at`
16. `updated_at`

### 5.2 字段语义

- `channel_type`
  - 枚举：`ONLINE | OFFLINE`
  - 用于区分线上渠道与线下渠道
- `platform`
  - 仅线上渠道必填
  - 线下渠道可为空
- `contact_name`
  - 渠道联系人
- `contact_phone`
  - 联系电话
- `contact_address`
  - 联系地址
- `commission_formula`
  - 平台抽佣公式
- `default_warehouse_id`
  - 默认发货仓库
- `allow_manual_order`
  - 是否允许手工建销售订单
- `allow_manual_after_sales`
  - 是否允许手工建售后订单

### 5.3 业务规则

1. 线上渠道必须选择平台
2. 线下渠道平台允许为空
3. 删除仅允许删除未被其它业务引用的渠道
4. 停用不等于删除，停用后仍可被历史数据引用
5. `去授权` 仅对线上渠道可用
6. 线下渠道右侧应明确提示“线下渠道无需授权”

## 6. 左侧筛选设计

左侧筛选必须使用统一工作台左侧过滤样式，但内容改为渠道域语义，不再复用订单审核树的订单业务概念。

4. 默认发货仓是否已配置
5. 是否允许手工建销售订单
6. 是否允许手工建售后订单
7. 部门
8. 负责人
9. 联系人

### 6.2 预置视图

建议内置以下快捷视图：

1. 全部渠道
2. 线上渠道
3. 线下渠道
4. 启用中
5. 已停用
6. 允许手工销售订单

2. 左侧筛选状态需进入保存视图/页面状态恢复
3. 左侧样式完全遵循一体化数据作业台统一约束
4. 左侧只承载筛选与统计，不承载业务动作

## 8. 顶部工具栏设计

### 8.2 业务动作

## 11. UI 页面存放规范

这是本次用户新增确认的强约束。

### 11.1 存放原则

渠道目录 UI 页面必须与其它二级目录页保持同级规范，不再延续混合式旧结构。

应遵循：

1. 页面域固定在 `apps/erp-web/src/pages/channels`
2. 目录页入口使用独立、语义明确的二级目录页面文件
3. 不再让“渠道目录”主页面继续承载店铺接入工作台语义

### 11.2 建议文件组织

建议整理为：

1. [ChannelDirectoryPage.tsx](/F:/erp/apps/erp-web/src/pages/channels/ChannelDirectoryPage.tsx)
   - 渠道目录主页面入口
2. `ChannelDirectoryPanels.tsx`
   - 左侧与右侧面板展示组件
3. `channelDirectoryModel.ts`
   - 渠道目录筛选、摘要、服务动作与数据转换逻辑
4. `channelDirectoryPage.css`
   - 渠道目录专属样式
5. `channelDirectoryColumns.tsx`
   - 渠道主表列定义
6. 对应测试文件

### 11.3 迁移策略

现有 [ChannelsPage.tsx](/F:/erp/apps/erp-web/src/pages/channels/ChannelsPage.tsx) 不应继续作为长期主入口文件。

推荐做法：

1. 由路由直接切到 `ChannelDirectoryPage`
2. 旧 `ChannelsPage` 退场或改成极薄兼容层
3. 后续若恢复店铺接入工作台，应独立到 `shops` 或 `channels/shops` 语义下

## 13. 错误处理

### 13.1 数据错误

1. 渠道列表加载失败，主表显示统一错误态
2. 仓库列表加载失败，相关下拉与详情使用降级展示
3. 右侧详情在无焦点记录时展示统一空态

### 13.2 动作错误

1. 新建失败，保留编辑内容并提示
2. 修改失败，保留编辑内容并提示
3. 删除失败，提示失败原因
4. 停用失败，提示失败原因
5. `去订购` 或 `去授权` 路由缺失时不得静默失败，应提示页面建设中

## 16. 最终结论

本次重构不是对现有渠道页做样式修补，而是一次主数据语义纠偏与统一工作台标准接入。

最终目标是：

1. `/channels` 成为真正的渠道目录
2. 页面主数据是销售渠道，而不是店铺
3. 页面结构完全服从一体化数据作业台统一规范
4. 页面文件组织对齐其它二级目录页
5. 右侧服务能力通过预留内部入口逐步扩展

这将为后续 `物流目录`、`供应商目录`、`仓库目录` 等二级目录页建立统一的工业级接入范式。
