# 顶部菜单共享二级面板设计

**日期**: 2026-04-16

## 目标

对 ERP 顶部菜单的二级菜单弹出体验进行工业级优化，核心目标只有一条：

- 不管点击哪个一级菜单，二级菜单弹出框的左边界、右边界、顶部基线和整体位置都保持不变
- 允许变化的只有面板内容与面板高度

本次优化要消除当前“二级弹层跟随触发项漂移”的体验，让顶部导航形成一个稳定、统一、可预期的系统级共享面板。

## 范围

本次设计只覆盖 `apps/erp-web/src/app/layout/AppLayout.tsx` 顶部 `header` 中的主菜单区域及其二级菜单弹出逻辑，重点包含：

- 一级菜单点击与展开行为
- 二级菜单共享面板的定位、宽度、高度与开合动画
- 当前路由对应的一级/二级高亮状态
- `Esc`、点击空白、重复点击当前一级菜单等关闭行为
- 响应式收缩下的固定边界策略
- 针对上述行为的单元测试与 E2E 回归测试

本次不改变业务菜单信息架构，不重排模块顺序，不改动顶部搜索、租户切换、用户菜单等无关区域。

## 现状与问题

当前顶部导航使用 Ant Design 的 `Menu` 横向菜单直接承载一级菜单与其子级结构。带子菜单的一级项会依赖组件默认弹层逻辑，在不同一级菜单上分别计算弹出位置。

这个实现会带来以下问题：

1. 二级菜单弹层的水平起点依赖触发项位置，不同模块打开后会左右漂移。
2. 弹层宽度和内容布局容易受到当前菜单项数量、分组长度和默认样式影响，缺乏工业级一致性。
3. 当用户在多个一级菜单之间切换时，视觉上会感知为“多个不同的下拉层”，而不是“同一个系统级功能面板在原位切换内容”。
4. 后续只要菜单文案、分组数量或响应式断点发生变化，就容易再次出现定位偏移或宽度抖动。

这说明问题的根源不是某个 CSS 数值不准，而是当前模型仍然把每个一级菜单都当成独立弹层的触发点。

## 设计结论

本次采用“顶部主菜单区域锚点 + 共享二级面板”的方案，替代当前依赖默认子菜单弹层的行为。

设计结论如下：

- 一级菜单仍保留横向导航的视觉形态与当前路由选中能力。
- 顶部导航只存在一个共享二级菜单面板，而不是每个一级菜单各自拥有独立弹层。
- 该共享面板的左边界、右边界、顶部基线统一对齐到顶部 `header` 内的主菜单区域。
- 点击不同一级菜单时，共享面板保持原位，仅切换内部内容。
- 共享面板的宽度随主菜单区域同步变化，但不随当前被点击的一级菜单变化。
- 面板唯一允许变化的是高度，且高度变化应当具有平滑过渡。

## 定位基准

### 1. 主菜单区域是唯一定位锚点

共享二级面板的定位基准明确为：

- 顶部 `header` 中承载一级菜单按钮的主菜单区域容器

这意味着：

- 面板左边界对齐该主菜单区域的左边界
- 面板右边界对齐该主菜单区域的右边界
- 面板顶部基线固定落在该主菜单区域下沿的统一位置

无论当前点击的是“销售”“仓储”“财务”还是其他一级菜单，都不得改写上述边界。

### 2. 不以触发按钮为定位依据

本次明确禁止继续使用“某个一级按钮自身的几何位置”作为二级弹层的最终水平定位依据。

允许一级菜单按钮继续承担点击打开与高亮交互，但不允许共享面板在视觉上锚定到某一个按钮的左边或右边。

### 3. 响应式下仍保持相同规则

当窗口宽度变化导致主菜单区域变窄或换行策略改变时：

- 共享面板宽度随主菜单区域收缩
- 共享面板仍只对齐主菜单区域边界
- 不退化为按当前触发按钮重新定位

## 交互规则

### 1. 有二级菜单的一级项

带二级菜单分组的一级项点击后：

- 打开共享二级面板
- 将当前一级项标记为展开态
- 在共享面板中渲染对应分组内容

如果共享面板此前已打开，再点击其他带二级菜单的一级项时：

- 面板保持打开
- 面板位置不变
- 面板内容切换为新的一级模块内容
- 面板高度根据新内容重新计算并平滑变化

### 2. 无二级菜单的一级项

没有二级菜单的一级项仍直接导航：

- 不打开共享面板
- 不进入共享面板切换逻辑
- 不因为共享面板存在而强制补一个空态层

### 3. 关闭行为

共享面板应支持以下统一关闭路径：

- 点击页面空白区域关闭
- 按 `Esc` 关闭
- 再次点击当前已展开的一级菜单关闭
- 点击二级叶子项并完成导航后关闭

关闭时只需要收起共享面板，不改变当前路由已有的一级/二级高亮逻辑。

### 4. 当前页面高亮

导航高亮遵循两层规则：

- 当前路由所属的一级菜单保持选中或激活态
- 共享面板中的当前叶子路由保持 `aria-current="page"` 与视觉高亮

若用户打开了非当前路由所属的一级菜单面板，但尚未点击叶子项，则：

- 当前路由的叶子高亮仍只归属当前页面路径
- 新打开的一级菜单表现为展开态
- 不提前伪造新的叶子选中状态

## 面板布局约束

### 1. 宽度

共享面板宽度由主菜单区域宽度直接驱动。

面板需要做到：

- 左右边界固定
- 内边距固定
- 分组列宽规则固定
- 内容切换时不发生横向抖动

### 2. 高度

共享面板高度是本次唯一允许变化的尺寸。

要求如下：

- 高度由当前模块内容的真实渲染高度决定
- 高度变化使用平滑过渡，而不是闪断式重算
- 切换模块时只出现纵向高度变化，不出现左右偏移或宽度闪动

### 3. 最大高度与滚动

当某些一级菜单分组较多或内容较高时：

- 共享面板自身应有统一最大高度
- 超出最大高度时，允许面板内部滚动
- 不允许因为菜单过长把整个 header 顶高
- 不允许弹层越出可视区后失去可用性

### 4. 工业化外观

共享面板应保持与当前 ERP 头部导航一致的工业化视觉语言，包括但不限于：

- 统一底色与边框层级
- 统一圆角与阴影
- 清晰的分组标题与分组间隔
- 二级叶子项具有稳定的悬停态、激活态和键盘焦点态

视觉重点应放在“稳”和“准”，而不是追求轻浮的浏览器下拉菜单效果。

## 状态模型

为支撑共享面板，顶部导航需要显式维护以下状态：

- `openModuleKey`
  - 当前处于展开态的一级模块
- `panelOpen`
  - 共享面板是否打开
- `activeModuleKey`
  - 当前路由归属的一级模块
- `panelRect`
  - 主菜单区域测量得到的定位数据，至少包含 `left`、`top`、`width`
- `panelHeight`
  - 当前内容区的实际高度，用于平滑过渡

其中：

- `activeModuleKey` 由当前路由推导，不应被点击临时状态覆盖
- `openModuleKey` 代表当前用户正在查看哪个一级模块的共享面板
- `panelRect` 只由主菜单区域测量结果驱动，不由当前按钮几何信息驱动

## 实现建议

### 1. 从“默认子菜单”改为“受控共享面板”

`AppLayout` 不应继续把二级菜单展开完全交给 Ant Design 默认子菜单弹层。

更稳妥的做法是：

- 将顶部菜单数据整理成“一级模块 + 二级分组 + 叶子项”的受控渲染结构
- 一级菜单按钮区域仅负责触发与高亮
- 在主菜单区域下方渲染一个共享面板容器
- 由组件状态驱动共享面板的显示、内容切换和高度动画

### 2. 主菜单区域测量

主菜单区域需要一个稳定的 `ref` 作为测量锚点。

在以下场景中需要重新同步共享面板位置和宽度：

- 首次打开共享面板
- 窗口尺寸变化
- 顶部 header 结构尺寸变化
- 一级菜单区域因响应式布局发生宽度变化

若某一帧暂未拿到有效测量结果，则应延后一帧打开，避免出现错误位置闪烁。

### 3. 高度测量与过渡

共享面板内容区应有独立内容容器用于测量真实高度。

推荐行为：

- 模块内容切换后读取内容实际高度
- 将外层面板高度过渡到新的像素值
- 关闭时再将高度过渡到折叠态

这样可以保证后续菜单树继续扩展时，无需手工维护某个模块的固定高度常量。

### 4. 数据测试标记

为了保证后续回归测试稳定，建议为共享面板与一级菜单触发器补充稳定标识，例如：

- 共享面板容器 `data-testid`
- 共享面板内容容器 `data-testid`
- 一级菜单按钮 `data-testid`
- 当前展开模块标记

## 测试策略

本次实现应遵循 TDD，并至少覆盖以下验证点。

### 1. 单元测试

针对顶部菜单结构与状态推导补充测试：

1. 当前路由能正确映射到所属一级模块
2. 无二级菜单的一级项点击后直接导航
3. 有二级菜单的一级项点击后只打开共享面板，不生成独立定位层
4. 共享面板切换不同一级模块时，定位边界数据不被触发按钮覆盖

### 2. 组件/交互测试

针对共享面板交互补充测试：

1. 点击当前展开一级菜单会关闭共享面板
2. 点击空白区域会关闭共享面板
3. 按 `Esc` 会关闭共享面板
4. 点击叶子项导航后会关闭共享面板
5. 当前页面对应叶子项具有稳定高亮

### 3. E2E 回归测试

新增或扩展 Playwright 用例，至少验证：

1. 打开两个不同一级菜单时，共享面板的 `left`、`right`、`top` 保持一致
2. 切换两个内容量不同的一级菜单时，共享面板高度发生变化
3. 切换模块时内容原位更新，不出现重新锚定到新按钮的横向跳动
4. 在窗口 resize 后再次打开共享面板，边界仍跟随主菜单区域而非按钮

## 本轮边界

### 包含

- 顶部主菜单共享二级面板改造
- 固定左右边界与顶部基线
- 只变高度的切换动画
- 顶部菜单相关单元测试与 E2E 回归测试

### 不包含

- 调整 ERP 顶部 header 其余工具区信息架构
- 改写业务菜单树的模块顺序与命名
- 改造全站其他页面中的 `Dropdown`、`Popover` 或右键菜单
- 新增与顶部菜单无关的视觉主题工程

## 风险与回退

本次改造的主要风险在于：

- 共享面板与现有 sticky header、tabs 区域的层级关系冲突
- 响应式布局下主菜单区域测量时机不稳定
- 测试如果只断言可见性而不校验几何边界，容易遗漏“位置仍然漂移”的回归

对应控制策略为：

- 显式定义共享面板层级与 header 内定位关系
- 将位置测量封装为稳定逻辑，并在 resize 时同步
- 在 E2E 中直接断言几何值一致性，而不是只断言面板存在

若实现过程中发现 Ant Design 默认横向 `Menu` 对共享面板受控渲染存在强耦合限制，则允许保留一级菜单的视觉样式，但改为自定义一级按钮渲染，以换取共享面板模型的稳定性。
