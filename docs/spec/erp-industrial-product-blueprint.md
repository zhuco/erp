> 目的：把现有功能目录、流程文档、上线门禁、Workbench/UI 规划收敛为单一权威产品目标文档。
>
> 合并来源：`docs/spec/erp-feature-catalog/*`、`docs/spec/erp-process-flows/*`、`docs/spec/*_updates_*.md`、`docs/ops/*`、`docs/web/*`、`docs/superpowers/specs/*`。
>

## 1. 产品定位

本项目的目标不是“能演示几个页面的电商后台”，而是面向真实商家、代运营团队、仓配组织与多店铺经营主体的工业级电商 ERP。目标产品需要同时覆盖交易链路、供应链链路、售后链路、财务链路与系统治理链路，并能支撑持续上线、可审计和多角色协同。

目标形态定义如下：

- 部署形态：优先支持 SaaS 多租户，同时兼容私有化与专有云交付。
- 经营形态：支持多平台、多店铺、多仓、多组织，逐步扩展到多商户、多公司结算。
- 业务形态：覆盖 B2C 电商、平台店铺、直营网店、仓配协同与售后逆向流程。
- 软件形态：前端不是菜单堆砌，而是围绕工作台、主数据、业务单据、任务和异常中心组织。

## 2. 设计原则

- 平台订单为准：外部平台状态是事实源，ERP 在其上做增强、编排与审计。
- 配置优先：规则、审批、字段、流程、编号、权限优先配置化，而不是散落在页面逻辑中。
- 数据闭环优先：任何单据变化都必须能回溯到来源、状态、责任人、时间和上下游影响。
- 多角色协同：运营、客服、仓库、采购、财务、管理者看到的是同一条业务链在不同视角下的工作台。
- 工业化门禁：上线必须以 OpenAPI、集成测试、E2E、审计、告警、发布门禁为准，不以“页面能打开”为准。

## 4. 目标信息架构（推荐菜单）

当前项目的页面数量已经很多，但产品信息架构还没有收敛。工业级 ERP 不应继续沿着“新增功能就多挂一个菜单”的方式扩张，而应按业务职责组织成稳定菜单。

### 4.1 推荐一级菜单

| 一级菜单 | 目标内容 |
| --- | --- |
| 首页 / 工作台 | 个人待办、异常中心、经营摘要、跨模块提醒 |
| 渠道与店铺 | 平台接入、店铺授权、同步任务、映射、下载任务 |
| 销售 OMS | 订单查询、审单、异常、拆合单、销售结算、订单设置 |
| 商品与主数据 | 商品、SKU、条码、单位、包装、套装、渠道可售、标签 |
| 采购与供应商 | 采购申请、采购计划、寻源、订单、收货、退货、供应商绩效 |
| 计划与补货 | 销售预测、安全库存、补货规则、采购补货、调拨建议、执行反馈 |
| 仓储 WMS | 基础资料、入库、库内作业、出库、波次、劳务、库位优化、补货任务 |
| 物流 TMS | 承运商、物流产品、运价、轨迹、异常、配送安装、物流结算 |
| 客户与售后 | 客户档案、会员、标签、分群、客服工单、售后单、平台售后、退款 |
| 财务结算 | 应收、应付、对账、开票、成本、费用分摊、利润、代销、税务 |
| 营销与价格 | 渠道价表、促销、赠品、优惠券、活动成本、活动复盘 |
| 经营分析 | 销售、发货、库存、利润、经营看板、导出任务 |
| 平台与集成 | 第三方接口、同步健康、打印设备、打印映射、集成审计 |
| 系统治理 | 用户、角色、权限、数据权限、流程配置、自定义字段、日志、可观测性 |

### 4.2 当前菜单的主要问题

- `财务` 挂在 `统计` 下，不符合企业用户的心智模型，也会削弱财务作为独立核心域的权重。
- `售后处理` 挂在 `客户` 下，适合 CRM 视角，但不适合作为 ERP 主业务域，需要在“客户与售后”中平级建模。
- `销售` 下同时塞入订单、网店下载、商品匹配、物流上传、包裹、策略设置，混杂了执行、接入、配置三类任务。
- `目录` 顶层过重，仓库、供应商、渠道、标签等主数据更适合归属到对应业务域或统一的“商品与主数据 / 平台与集成”。
- `系统` 下出现 `AG Grid Enterprise` 这类研发或演示性质入口，不适合作为生产版菜单暴露给业务用户。
- `服务` 只有打印，说明打印能力尚未被归入仓储、物流或平台服务的正式产品结构。

## 5. 核心业务闭环

### 5.1 Order to Cash

渠道授权 -> 拉单 / Webhook -> 标准化 -> 审单与异常 -> 拆合单 -> 预占库存 -> WMS 出库 -> 物流回传 -> 对账 -> 收款 / 开票 -> 利润归集。

### 5.2 Procure to Stock

补货需求 -> 采购申请 -> 采购订单 -> 到货 -> 收货 -> 质检 -> 上架 -> 成本入账 -> 库存可售。

### 5.3 Plan to Replenish

销售预测 -> 安全库存 -> 补货规则 -> 采购 / 调拨建议 -> 执行反馈 -> 预测校正。

### 5.4 Return to Resolution

客户申请 -> 售后审核 -> 退款拦截 / 换货补发 / 退货入库 -> 质检 -> 财务回写 -> 责任归因与 SLA 关闭。

### 5.5 Record to Report

业务单据 -> 台账与事件 -> 成本 / 费用归集 -> 对账与核销 -> 经营驾驶舱 -> 发布门禁与审计追踪。

## 6. 上线分层

### 6.1 P0：首个可收费上线版本

适用目标：单主体或单商户、多店铺、多仓的首批付费客户上线。

必须具备：

- 稳定的平台接入、OAuth、Webhook 验签、同步补偿、失败重试。
- 订单主链路闭环：接单、审单、异常、库存占用、出库、物流、售后回写。
- 仓储主链路闭环：入库、上架、拣货、复核、打包、发货、盘点、调拨。
- 商品主数据与渠道映射闭环。
- 基础财务闭环：对账、发票、利润、费用分摊至少可形成经营核算。
- RBAC、数据权限、审计日志、失败队列、可观测性和发布门禁。

### 6.2 P1：稳定经营版本

适用目标：多个品牌 / 多组织稳定使用，支撑运营、仓库、采购、财务多部门协同。

必须增强：

- 采购与计划能力从“页面存在”提升到可执行闭环。
- 售后、客服、客户画像、会员、工单形成客户经营视角。
- 物流运价、物流结算、仓配优化、配送安装等增值能力。
- 自定义字段、审批中心、编号规则、流程版本化管理。
- 经营驾驶舱、异常 SLA、库存预警、销售预测准确率反馈。

### 6.3 P2：工业化平台版本

适用目标：多商户、多公司、多事业部、多仓配网络的大中型客户。

必须补齐：

- 多商户层与多法人结算模型。
- 组织、审批、任务协同、质量体系、知识沉淀。
- 更完整的财务口径、期间结账、跨组织对账、税务规则。
- 面向移动终端 / PDA / 仓内设备的执行闭环。
- 更细粒度的 SLO、容量治理、灰度发布与配置审计。

## 7. 非功能要求

| 能力项 | 工业化要求 |
| --- | --- |
| 安全 | 租户隔离、权限校验、密钥管理、日志留痕、关键动作审计 |
| 一致性 | Inbox/Outbox、幂等键、状态不可逆校验、补偿任务 |
| 可观测性 | Trace、Metrics、日志、失败队列、集成 SLA、业务告警 |
| 上线门禁 | OpenAPI 校验、后端集成测试、前端构建、E2E、发布清单 |
| 性能 | 面向高订单量的分页、虚拟滚动、懒加载、异步任务处理 |
| 可配置性 | 编号、流程、字段、审批、规则、标签、看板配置化 |
| 可审计性 | 用户、角色、数据权限、关键业务动作、状态变化全量记录 |
| 灾备 | 备份、恢复演练、数据保留策略、故障处理 Runbook |
